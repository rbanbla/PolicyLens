# PolicyLens 데이터 계획

작성일 2026-11-06, 범위 갱신일 2026-11-07. 상태는 **기존 서버 자료 67건 운영 중, 전국 청년 정책 원문 확대 수집 중, 정답 라벨은 초안**이다. 과제 Topic 6의 데이터 요구(사회적으로 중요한 주제의 국내외 정책 문서)를 어떻게 충족할지 정리한다. 실제 수집 결과는 9절에 기록한다.

## 1. 요약

데이터는 쓰임에 따라 네 가지로 나눈다. 실행 중 에이전트를 바꾸는 것은 S뿐이다. P와 G는 입력이나 평가에만 쓰여 에이전트의 판단 자체를 바꾸지 않는다.

| 구분 | 무엇 | 왜 필요한가 | 어디에 쓰나 | 필요성 |
|---|---|---|---|---|
| **S. 서버 자료** | 검수를 통과해 적재한 정책 문서와 공개 의견 | 에이전트가 입력 문서 밖의 사실과 실제 문제를 확인 | 실행 중 `search_sources`, `read_source` 도구 | 필수(적재됨) |
| **P. 평가 문서** | 발행된 시행계획, 사업·모집공고 등 원문 | 서비스 입력이자 평가 대상 | 업로드해서 파이프라인 실행 | 필수 |
| **G. 실제 기록** | 공고 뒤에 벌어진 일을 담은 공식 공지, 공개 회의록의 발언 | 모델이 찾은 이해관계자와 쟁점이 실제와 맞는지 확인 | 평가 정답(Gold) | 필수(초안) |

평가의 핵심 구조는 **문서 하나에 실제 기록이 연결된 쌍**이다. 공고만 읽고 그 뒤 실제로 벌어진 문제를 미리 짚어내는지를 본다. 같은 자료가 서비스에서는 S로, 평가에서는 G로 쓰이며 둘을 나누는 기준은 발행일이다(7절).

## 2. 수집 및 평가 범위

2026-11-07 사용자 요청으로 수집 범위를 청년 관련 세금, 주거·부동산, 대학·장학·학자금, 취업·창업, 금융·복지·문화 혜택 전반으로 확대했다. 국무조정실의 2026년 중앙행정기관 시행계획과 과제카드, 17개 시도 시행계획 공식 묶음을 우선 확보하고 개별 기관의 공고·업무처리기준을 보완한다. 아래 6건은 기존 평가 표본이며 확대 수집량과 별도로 관리한다.

사용자가 확정한 범위는 전국 모든 지자체의 2026년 적용 문서다. 전국 완전 수집 여부는 공식 목록의 기관·과제와 수집 원본을 대조해 판단한다. 시행계획 확보는 개별 사업의 모든 모집·정정 공고 확보와 구분해서 기록한다. 새 자료는 수집 명세에 등록하고 기존 기술·권리 검수를 거쳐 서버에 적재한다.

### 주제와 수량

국내에서 정식 발행된 청년 정책을 두 갈래로 나눠 3건씩, 총 6건을 평가 목표로 삼는다.

| 주제 | 목표 | 포함 범위 | 살펴볼 쟁점 |
|---|---:|---|---|
| 청년 정책 | 3건 | 일자리·취업, 생활·복지, 자산형성 지원 | 연령·소득·취업 조건, 중복 수혜, 선정 우선순위 |
| 청년 부동산 정책 | 3건 | 청년을 대상으로 명시한 월세·보증금·이사비 지원과 공공임대 공급 | 무주택·가구 기준, 임차조건, 배점·우선 공급, 임대인·집행기관 역할 |

P의 범위는 한국어로 발행된 시행계획, 사업공고, 모집공고, 시행 중인 관련 고시·조례다. 청년·대학생·초기 사회진입자에게 적용되는 대상과 조건이 확인되는 세금·교육·주거·혜택 문서를 수집한다. 입법예고안은 발행된 시행 정책의 평가 후보에서 제외한다. 여러 분야에 걸치는 문서는 지원의 주목적에 따라 한 갈래에만 등록한다.

### 문서 다양성 기준

- 짧은 모집공고와 상세 시행계획·모집요강을 섞고, 중앙부처·공공기관·지자체 발행 문서를 고르게 찾는다.
- 양자 구조 문서를 최소 1건 넣는다. 역할 2명 경로를 시험하기 위해서다.
- 영향받는 집단이 문서에 이름 없이 숨어 있는 문서를 최소 1건 넣는다. `implied` 역할 시험용이다.

## 4. 수집 절차

공식 묶음 파일은 일괄 확보하고 기관·분야·연도와 원본 해시로 추적한다. 개별 공고는 판본과 내용 확인을 거쳐 보완한다. 평가 표본 6건의 검토와 서버 참고자료 확대 수집을 별도로 집계한다.

1. **후보 등록:** 주제별 후보를 2배수로 찾아 `candidates.csv`에 URL과 함께 적는다.
2. **원본 저장:** 원본 파일을 받아 SHA-256과 수집 일시를 기록한다. 원본은 수정하지 않는다.
3. **텍스트 변환:** 서비스와 같은 `read_pages`로 변환한다. 평가 입력과 실제 사용 경로가 달라지지 않게 하기 위해서다.
4. **기술·권리 검증:** 5절의 관문 1·2 판정을 기록한다.
5. **의견 수집과 내용 검증:** 같은 정책·판본에 연결된 의견을 모으고 개인정보를 제거한 뒤 관문 3을 판정한다.
6. **정답 라벨링:** 7절 절차대로 모델 실행 **전에** 라벨을 확정한다.

## 5. 적합성 검증

문서는 세 관문을 차례로 통과해야 한다. 판정은 통과, 보류, 제외 중 하나이며 사유를 기록한다.

### 관문 1. 기술 검증 (자동)

| 항목 | 기준 |
|---|---|
| 텍스트 추출 | `read_pages` 성공. 80쪽, 10만 자 이하 |
| 스캔 여부 | 빈 쪽 비율 10% 이하 |
| 깨짐 | 샘플 인용 5개가 `check_quote`를 통과 |
| 중복 | SHA-256이 기존 문서와 다름 |

서비스 입력은 PDF, TXT, 붙여넣기다. 수집 단계의 HWP와 HWPX는 본문을 추출해 처리본으로 저장한다. 표는 줄 단위로 풀리므로 원문과 대조한다. 스캔 문서는 OCR이 없으므로 제외한다.

### 관문 2. 출처와 권리 검증 (사람)

| 항목 | 기준 |
|---|---|
| 공식성 | 발행 기관의 공식 사이트나 API에서 받은 원본 |
| 판본 | 공고번호·적용연도·모집회차, 정정 여부와 정정 일자를 기록 |
| 이용 조건 | 공공누리 유형이나 약관 기록. 변경 금지 유형은 재게시와 재배포 범위를 따로 검토 |
| 외부 전송 | 모델 제공자에게 보내도 되는지 승인 기록. 비공개 자료와 개인정보는 전송 금지 |

### 관문 3. 내용 검증 (사람 2명)

| 항목 | 기준 |
|---|---|
| 논쟁성 | 이해가 갈리는 집단이 둘 이상이고, 쟁점 유형에 해당하는 조항이 3개 이상 |
| 의견 충분성 | 서로 다른 입장의 G가 2종류 이상, 합계 5건 이상 |
| 시의성 | 시행일과 개정 이력을 확인하고 폐지된 문서는 명시 |
| 편중 방지 | 같은 소관 기관이나 같은 쟁점에 몰리지 않음 |

의견 충분성을 통과하지 못해도 P로는 쓸 수 있다. 다만 G 기반 지표에서는 제외하고 그 사실을 보고서에 적는다.

### G 자료 추가 검증

- **개인정보:** 개인 이름, 연락처, 주소를 제거한다. 공개된 단체명은 유지한다.
- **작성자 유형:** 개인, 단체, 기관으로 구분한다. 표시가 없으면 `unknown`으로 두고 추정하지 않는다.
- **중복:** 같은 문구가 반복된 캠페인 의견은 묶어서 1건으로 세고 건수를 함께 기록한다.
- **주제 일치:** 의견이 어느 문서의 어느 판본을 향한 것인지 확인한다.
- **대표성:** 의견을 낸 사람은 스스로 참여한 집단이다. **의견 수를 여론으로 해석하지 않는다.**

## 6. 저장 구조

기존 폴더를 그대로 쓴다. `data/` 아래 내용은 `.gitignore`로 저장소에서 제외되므로, 팀 공유는 별도 비공개 공간을 쓴다.

```text
data/
├── raw/<doc_id>/              # 원본 파일. 수정 금지
├── processed/<doc_id>/
│   └── pages.json             # read_pages 결과
└── reviewed/
    ├── candidates.csv         # 후보와 탈락 사유
    ├── documents.jsonl        # 관문을 통과한 문서
    ├── opinions.jsonl         # 정제한 실제 의견
    └── annotations.jsonl      # 평가 정답 라벨
```

문서 ID는 `주제-국가-일련번호` 형식이다. 예: `youth-kr-05`, `youth-housing-kr-01`. 앞서 사용한 ID는 재사용하지 않는다.

### documents.jsonl

```json
{
  "doc_id": "youth-kr-05",
  "kind": "policy",
  "topic": "청년 정책",
  "country": "KR",
  "title": "문서 제목",
  "issuer": "발행 기관",
  "doc_type": "모집공고",
  "version": "2026년 1차 모집공고",
  "published_on": "2026-08-04",
  "language": "ko",
  "source_url": "https://...",
  "retrieved_at": "2026-11-06",
  "sha256": "...",
  "license": "공공누리 제1유형",
  "external_send_ok": true,
  "gate": {"technical": "pass", "rights": "pass", "content": "pass"},
  "notes": ""
}
```

### opinions.jsonl

```json
{
  "opinion_id": "youth-kr-05-op-003",
  "doc_id": "youth-kr-05",
  "source_type": "공개 의견서",
  "author_type": "단체",
  "author_group": "구직 청년",
  "stance": "반대",
  "clause_refs": ["제5조"],
  "text": "개인정보를 제거한 원문",
  "duplicate_count": 1,
  "source_url": "https://...",
  "submitted_on": "2026-08-10",
  "review_status": "reviewed"
}
```

### annotations.jsonl

```json
{
  "doc_id": "youth-kr-05",
  "stakeholders": [
    {"group": "구직 청년", "in_document": true, "evidence": ["youth-kr-05-op-003"]}
  ],
  "issues": [
    {"issue_id": "I1", "clause_refs": ["제5조"], "signal": "부담 전가", "groups": ["구직 청년", "사업 운영기관"], "evidence": ["youth-kr-05-op-003"]}
  ],
  "annotators": ["A", "B"],
  "fixed_at": "2026-11-10"
}
```

`in_document`가 `false`인 집단이 `implied` 역할의 정답이 된다. 실제 파일에는 `status`(draft, fixed)와 사람 채점 전 대략 비교에 쓰는 키워드 `match`가 더 있다. `kind`는 policy 또는 opinion이다. 연구보고서는 opinion으로 둔다. `opinions.jsonl`의 `reviewer`에 누가 무엇을 확인했는지 적는다.

## 7. 사용 방법

### P. 평가 입력

`manage.py evaluate <doc_id>`가 `data/processed`의 문서를 서비스와 같은 파이프라인으로 실행하고 결과를 `data/reviewed/runs/`에 저장한다. `--no-sources`는 서버 자료를 끈 조건이다. 사용자의 입력 방식은 바뀌지 않는다. 서비스에 정책 목록이나 추천을 넣지 않는다.

**평가 실행은 문서 발행일 이전의 정책 자료만 본다.** 공고 뒤의 공지와 의견은 정답이므로 숨긴다. 날짜가 없는 자료도 숨긴다. 그 결과 평가에서는 의견 자료의 효과를 재지 않는다.

문서마다 G가 가장 많은 입장을 사전에 하나 정해 그 입장으로 실행한다. 서버 자료의 효과와 파이프라인 구조의 효과를 구분하기 위해 같은 문서를 서버 자료를 끈 조건으로도 실행한다. 비용을 줄이면서 평가 입장을 임의로 고르지 않기 위해서다.

### G. 평가 정답

**순서가 중요하다. 모델 결과를 보기 전에 정답을 확정한다.** 결과를 본 뒤 라벨을 만들면 모델에 유리하게 기울 수 있다.

1. 두 사람이 G를 읽고 각자 이해관계자와 쟁점을 라벨링한다.
2. 일치도를 계산하고 불일치를 협의해 정답을 확정한다.
3. 모델을 실행하고 지표를 계산한다.
4. 같은 문서와 입장의 단일 프롬프트 결과도 같은 기준으로 채점한다.

`manage.py score`는 사람 채점 전의 대략 비교다. 정답 쟁점의 키워드 두 묶음이 300자 안에 함께 나오면 언급으로 센다. 타당성을 판단하지 못하므로 결과 보고에 초안임을 밝힌다.

| 지표 | 측정 내용 | 계산 |
|---|---|---|
| 이해관계자 재현율 | 실제 의견을 낸 주요 집단을 찾았는가 | 찾은 정답 집단 / 정답 집단 |
| 역할 타당도 | 제시한 역할이 실제 당사자인가 | 근거 있는 역할 / 제시 역할 |
| `implied` 재현율 | 문서에 없는 집단을 찾았는가 | 찾은 숨은 집단 / 숨은 집단 |
| 쟁점 재현율 | 실제 논쟁 조항을 찾았는가 | 찾은 정답 쟁점 / 정답 쟁점 |
| 쟁점 정밀도 | 고른 쟁점이 실제 쟁점이거나 타당한가 | 타당한 쟁점 / 제시 쟁점 |
| 인용 정확도 | 인용이 원문에 있고 주장을 뒷받침하는가 | 타당한 인용 / 전체 인용 |
| 토론 구체성 | 역할 이름을 바꾸면 성립하지 않는 발언인가 | 구체적 발언 / 전체 발언 |

G에 없는 쟁점을 곧바로 오답으로 처리하지 않는다. G는 실제 의견의 일부일 뿐이므로 평가자가 원문을 보고 타당성을 판단한다. 표본이 작으므로 지표는 경향으로만 보고하며 통계적 일반화를 주장하지 않는다.

### S. 서버 자료

에이전트 사용 방식은 [제품 계획](PRODUCT_PLAN.md)의 서버 자료 활용 절을 따른다. 적재는 `manage.py load_sources`로 한다. `documents.jsonl`에서 기술·권리 관문을 통과하고 `external_send_ok`가 참인 문서와, `opinions.jsonl`에서 그 문서에 연결되고 `review_status`가 `reviewed`인 의견만 올린다. 관문을 잃은 자료는 같은 명령이 지운다. 내용 관문은 평가 기준이므로 적재 조건이 아니다.

- 공고들이 서로 언급하는 사업을 따라 묶음으로 모은다. 양보다 연결이 중요하다.
- 평가 대상 문서 자체는 서버에 있어도 된다. 실행 중 입력과 내용이 같은 자료는 근거에서 제외된다. 줄바꿈 외의 내용이 다르면 제외되지 않으므로 평가에서는 같은 원문을 입력한다.
- 프롬프트를 고칠 때 본 문서는 최종 평가에서 뺀다. 정답이 있는 문서가 3건뿐이라 이번 평가에서는 지키지 못했고 [구현 상태](IMPLEMENTATION_STATUS.md)에 한계로 기록했다.

### 쓰지 않는 방식

- 모델 학습에 쓰지 않는다.
- 합성 토론 결과를 근거로 승격하지 않는다.
- 의견 수를 모델이나 화면에서 찬반 비율로 제시하지 않는다.
- 사용자가 올린 문서를 평가 데이터로 재사용하지 않는다.

## 8. 위험과 대응

| 위험 | 영향 | 대응 |
|---|---|---|
| 공고에 공개 의견 창구가 없음 | G 부족 | 시의회 회의록과 후속 공지를 쓰고, 그래도 부족한 문서는 P 단독으로 분류 |
| 시의원 발언이 곧 당사자 의견은 아님 | 청년 본인의 목소리가 빠짐 | 의원은 대리 발언자로 표시. 참여자 조사 보고서로 보완하고 한계를 명시 |
| G가 조직된 집단에 치우침 | 정답이 편향됨 | 약자 집단 누락 가능성을 한계로 명시. `implied`는 원문으로 별도 판단 |
| 라벨러가 2명뿐 | 정답의 주관성 | 불일치를 기록하고 라벨 근거를 의견 ID로 연결 |
| 표가 많은 문서의 추출 오류 | 소득 기준 같은 핵심 조항 손실 | 관문 1에서 표 샘플을 원문과 대조 |
| 정책 변경으로 문서가 낡음 | 잘못된 안내 | 판본과 수집일 표시. 평가 결과를 현행 조언으로 쓰지 않음 |
| 이용 조건 위반 | 재배포 문제 | 원문을 저장소와 공개 화면에 올리지 않음. 약관 재확인 |

## 9. 작업 순서

1. 발행기관과 공고번호·연도·회차를 확인하고 주제별 후보를 2배수까지 등록
2. P 원본을 저장하고 기술·권리 관문을 검증
3. 같은 정책·판본에 연결되는 G 수집, 정제, 개인정보 제거
4. 검토자 2명이 내용 관문을 검증하고 P 단독과 P–G 평가 대상을 확정
5. 두 명이 정답 라벨 확정
6. PolicyLens와 단일 프롬프트 실행, 지표 계산
7. 결과를 보고 공개 의견을 서버 자료로 넓힐지 결정
