# 구현 상태

2026-11-06 기준. 이 프로젝트는 자체 가상환경과 데이터로 단독 실행되며 다른 프로젝트에 의존하지 않는다.

## 현재 동작

공공정책 문서를 PDF, TXT, 붙여넣기로 받아 이해관계자 2~3명을 추출하고, 역할별 독립 입장, 쟁점 정리, 쟁점 토론을 거쳐 내 입장의 주의 조항과 역할별 의견서를 만든다. 5페이지에서 단일 프롬프트 결과와 비교 평가할 수 있다.

- **파이프라인:** 단계 순서는 서버가 고정한다. 단계별 JSON 스키마, 원문 인용 검증, 참조 ID 검증, 오류를 돌려주는 수정 재호출 1회를 적용한다.
- **서버 자료:** 역할 에이전트와 최종 정리는 첫 호출에서 검색이 강제되고 토론은 선택이다. 역할 추출과 쟁점 정리는 쓰지 않는다. 라운드는 3회로 제한하고 상한에 닿으면 도구 없이 답을 받는다. 서버 자료의 인용도 원문과 대조하며, 실행 당시 출처를 결과에 함께 저장한다.
- **검색:** 키워드 검색이다. 공백이 깨진 PDF 글자, 긴 낱말의 앞부분(국토교통부와 국토부), 최근 1년 자료를 반영한다. 입력 문서와 내용이 같은 자료는 제외한다.
- **평가:** `evaluate`는 문서 발행일 이전의 정책 자료만 보고 실행한다. `score`는 키워드로 대략 비교한다.
- **기록:** 실행별 입력, 모델, 프롬프트, 호출별 시간과 토큰, 오류, 검색 기록을 저장한다.
- **복구:** 시간 초과는 서버가 한 번 다시 보낸다. 그래도 실패하면 저장된 단계에서 사용자가 재시작한다.

## 데이터

서버 자료 67건(정책 34, 의견 33)을 적재했다. 평가 문서는 6건이고 정답 초안은 3건, 쟁점 12개다. 내용과 한계는 [데이터 계획](DATA_PLAN.md) 9절에 있다.

## 평가 결과

정답 초안의 쟁점 중 결과가 언급한 수의 평균이다. 조건마다 3회 실행했고 단일 프롬프트는 6회다. 사람 채점이 아니라 키워드 비교이며 정답도 확정 전이다. 평가에서는 공고 뒤 자료와 의견 자료를 숨기므로 서비스에서의 서버 자료 효과를 재지 않는다. 프롬프트 수정 전 21회는 `data/reviewed/runs-before-prompt-fix/`에 보관했고 그때 합계는 문서만 6.67, 서버 자료 7.67, 단일 프롬프트 9.67이었다.

| 문서 | 쟁점 | 문서만 | 서버 자료 | 단일 프롬프트 |
|---|---:|---:|---:|---:|
| 서울 청년월세 | 5 | 2.67 | 2.67 | 3.83 |
| 서울 청년수당 | 5 | 2.67 | 2.67 | 3.50 |
| 희망두배 청년통장 | 2 | 1.33 | 1.33 | 1.83 |
| 합계 | 12 | 6.67 | 6.67 | 9.17 |

- **단일 프롬프트가 이 기준에서 가장 높다.** 단일 프롬프트는 긴 목록을 나열하고 PolicyLens는 주의 조항 3~6개를 제시한다. 이 점수는 넓게 나열할수록 유리하고 초점, 판단의 질, 인용 정확도는 재지 못한다. 그래도 PolicyLens가 실제 쟁점을 더 많이 찾는다는 근거는 없다.
- **서버 자료의 효과는 이 평가에서 보이지 않는다.** 합계가 같고 실행별 값도 겹친다.
- **5페이지 글이 줄었고 항목 수도 줄었다.** 정답 문서 기준 글자 수 중앙값은 서버 자료 3,612자에서 2,862자로 21%, 문서만 3,681자에서 2,460자로 33% 줄었다. 주의 조항이 4개 이하인 실행이 4회에서 10회로 늘어, 줄어든 양의 일부는 항목 수에서 왔다. 점수 변화와의 인과는 확인하지 않았다.
- **역할은 안정됐다.** 21회 모두 3명이고 모두 집행기관을 포함한다. 서울 청년월세는 6회 중 5회가 1인 가구와 특수유형으로, 서울 청년수당은 6회 중 5회가 미취업과 단기근로로 나뉘었다. 희망두배 청년통장은 일부가 여전히 선정·제외로 나뉜다. 문서에 없는 implied 역할은 63개 중 0개다.
- **비용은 서버 자료 조건이 크다.** 정답 문서의 토큰 중앙값은 서버 자료 19.6만, 문서만 14.1만이다. 호출은 서버 자료 14~17회, 문서만 10~11회다(단일 프롬프트 1회 포함).
- **자료를 쓰는 비율이 낮다.** 서버 자료 조건 12회에서 실행당 검색은 4~8회, 인용은 0~4건이고 5회는 인용이 없다. 토론 에이전트는 한 번도 검색하지 않았다.
- **평가 규칙을 지키지 못했다.** [데이터 계획](DATA_PLAN.md)은 프롬프트를 고칠 때 본 문서를 최종 평가에서 빼라고 한다. 실제로는 평가 문서 결과를 보고 검색과 프롬프트를 고친 뒤 같은 문서로 평가했다. 수치가 유리하게 나왔을 수 있다.

서비스 모드에서는 평가에 없는 자료까지 쓴다. 서울 청년월세 공고로 웹 흐름을 진행했을 때 역할 에이전트가 서울시와 국토부 중복 선정자의 지급중지 공지를 찾아 환수 위험이 실제로 발생했다고 썼고, 국회예산정책처 결산 분석과 서울시 입장 자료를 인용했다. 다만 1회 실행의 사례이고 결과가 나아졌는지는 측정하지 않았다.

## 실제 시험에서 발견해 고친 결함

- 모델이 문서에 인쇄된 쪽 번호를 인용해 긴 TXT의 역할 추출이 실패했다. 인용문이 있는 쪽으로 서버가 맞춘다.
- 도구를 선택 사항으로 두면 역할 에이전트가 쓰지 않았다. 첫 호출에서 강제한다.
- 병렬 도구 호출을 나눠 보내 HTTP 400이 났다. 호출들을 한 메시지로 합친다.
- 인용 오류 메시지가 어느 인용인지 말해주지 않아 수정 재호출이 실패했다. 쪽과 앞부분을 넣었다.
- 검색이 국토교통부로 찾으면 국토부라고 쓴 공지를 놓쳤고 옛 공고가 최신 공지를 밀어냈다. 긴 낱말의 앞부분과 최근 자료 가산을 넣었다.
- 공고의 가운뎃점과 물결표 변형, 보이지 않는 문자 때문에 같은 문장이 인용 검증에서 거부될 수 있었다. 비교 전에 지운다. 실패한 실행의 전체 인용을 확보하지 못해 원인은 추정이다.
- 엔드포인트가 간헐적으로 요청 하나를 멈췄다. 같은 요청을 다시 보내면 15초 안에 끝났다. 시간 초과를 90초로 두고 한 번 다시 보낸다.
- 대학 AI 윤리 가이드라인의 반각 가운뎃점(U+FF65) 때문에 맞는 인용이 거부되어 토론이 멈췄다. 비교 전에 지우는 문자에 넣었다.

최종 평가 21회에서 전체 실행을 다시 돌린 경우는 인용 문구가 바뀐 1건이다. 별도로 평가 도중 네트워크가 끊겨 12회를 다시 돌렸다. 가운뎃점 수정은 평가 뒤에 했고, 인용을 더 넓게 받는 변경이어서 평가를 다시 돌리지 않았다.

## 검증

Django 테스트 65개 통과, 마이그레이션 0006 적용, 시스템 검사 통과. 프로젝트 전용 `.venv`에서 실행했다. 최종 코드로 실제 모델을 써서 서울 청년월세 공고의 웹 흐름을 끝까지 진행했다. 호출 12회 중 1회가 멈췄다가 자동 재시도로 복구되었고, HTTP 오류와 브라우저 콘솔 오류는 없었다. 5페이지 근거, 찾아본 기록, 의견서, 비교 화면을 확인했고 390px에서 가로 넘침이 없다. Chat Completions 호환 엔드포인트(gpt-5.6-luna)로만 시험했고 Responses 모드의 도구 호출은 모의 시험뿐이다.

대학 AI 활용 윤리 가이드라인(37쪽 PDF)을 사용자 요청으로 지정 엔드포인트에 보내 학습자 입장으로 시험했다. 이 문서는 서버 자료에 넣지 않았다. 최종 코드의 웹 흐름은 호출 15회(비교 포함), 36만 토큰에 시간 초과와 HTTP·브라우저 오류가 없었고 인용 수정 재호출이 1회 있었다. 서버 자료 인용은 없었다. 문서가 자율 가이드라는 성격은 프롬프트 수정 뒤 전체 실행 3회 모두 언급됐지만 2회만 별도 주의 조항이었다. 과제 입력 금지 조항은 3회 모두 별도 주의 조항으로 나오지 않았다.

5페이지 글 양을 항목별 목표 글자 수로 줄였다. 같은 앞 단계 결과로 최종 정리만 다시 돌린 결과 주의 조항 글자 수가 위 가이드라인 2회에서 21%, 25%, 서울 청년월세 2회에서 16%, 29% 줄었고 수정 재호출은 없었다. 모바일 5페이지 높이는 5,479px에서 5,070px로 7% 줄었다. 비교 화면은 두 결과를 같은 높이의 상자에 넣고 단일 프롬프트 쪽 마크다운 기호를 지워 데스크톱 높이가 6,423px에서 1,637px로 줄었다. 단일 프롬프트 답변의 내용은 비교 기준이므로 줄이지 않았다.

## 알려진 한계

- 인용 검증은 문구의 존재만 확인하고 주장을 뒷받침하는지는 판단하지 않는다. 역할의 red_line에서 문서에 없는 전제가 섞인 사례가 있었고 이를 잡는 장치는 없다.
- 평가는 실행한 세션 소유자만 할 수 있고, PolicyLens 과정을 본 뒤 평가하므로 맹검이 불완전하다. 사람 평가자의 비교는 아직 없다.
- 의견 자료의 대부분은 시의원 발언이다. 청년 본인의 공개 의견은 조사 보고서뿐이고, 시민단체 성명과 청원은 찾지 못했다.
- 검색은 전체 자료를 메모리에서 훑는다. 지금 규모에서 0.04초이고 자료가 크게 늘면 전문 검색으로 바꿔야 한다.
- 실행은 동기 호출이고 SQLite 트랜잭션 안에서 진행된다. 다중 사용자 운영에는 PostgreSQL, 워커, 동시 실행 제어가 필요하며 구현하지 않았다.
- 상황 메모와 쟁점 선택 입력은 2·3페이지 디자인 유지 지시에 따라 넣지 않았다.
- 같은 문서라도 역할을 나누는 기준과 주의 조항은 실행마다 달라질 수 있다.
- `docs/previews/`의 화면은 서버 자료 표시 이전이다.
- 턴제는 단계가 3명 기준 8개에서 20개가 되고, 서버 자료 검색 라운드를 포함한 모델 호출은 32~37회(이전 12회 중앙값 13.5회), 총 호출 시간 218~235초(이전 중앙값 147초), 토큰 약 51만~58만(이전 중앙값 약 19.9만)이다. 문서 전문을 매 호출에 보내므로 긴 문서에서 비용이 크다. 청년월세 공고 한국어·영어 실행 각 1회의 실측이며 표본이 작다.
- 의견 하나짜리 턴도 빠르지 않다. 독립 입장 턴은 중앙값 12~14초(최소 7초, 최대 30초)로, 턴마다 서버 자료 검색이 거의 한 번씩 들어가서 5~6초 추정에 못 미쳤다. 토론 턴은 중앙값 6~7초다. 3쪽 전체는 약 121~132초, 4쪽은 56~65초다(이전 중앙값 61초, 49초). 쟁점 정리는 한 번의 호출이라 화면이 말풍선을 3초 간격으로 나눠 보여준다.
- 이전 방식으로 만든 실행은 새 단계 계획과 맞지 않아 이어갈 수 없다. 앞 단계 번호와 종류가 달라 새 문서로 다시 시작해야 한다.
- 토론 대화 구조는 대학 AI 윤리 가이드라인 1건에서 토론 9턴을 실제 모델로 재생해 확인했다. 표본이 작다. 재생 중 프롬프트가 `target_ids` 필드를 뭉뚱그려 지시했을 때 모델이 `issue_id`를 재시도까지 빠뜨려 멈춘 적이 있어 필드 이름을 밝혔고, 그 뒤 9턴은 재시도 없이 끝났다. 멈추더라도 재시작 버튼으로 그 턴부터 이어진다.
- 글자 수는 프롬프트 지시일 뿐 서버가 막지 않는다. 길다고 검토를 멈추는 것이 더 나쁘다고 판단했다. 한자는 서버가 거부해 재시도하며, 문서 자체에 있는 한자와 인용은 허용한다.
- 텍스트를 붙여넣은 문서는 제목이 없어 "정책 검토"로 표시된다. 파일은 파일 이름을 쓴다.
- 쟁점 토론 도중에 멈춘 이전 실행을 이어가면 발언 순서가 새 계획과 어긋날 수 있다. 끝난 실행의 표시에는 영향이 없다.
- 영어 출력은 실제 모델로 1회 완주해 확인했다. 본문은 영어, 검색어는 한국어, 인용은 원문 그대로였다. 글자 수 지시는 지키지 않았다(독립 입장 reason 평균 527자로 목표 약 300자의 1.8배, 역할 이름 28~32자). 영어 실행은 20단계 중 2단계가 서버 자료 인용 검증에서 첫 시도에 실패해 재시도가 필요했고 한국어 실행은 0회였다. 표본이 1회씩이라 일반화할 수 없다.
- 언어는 업로드 때 한 번 정해지고 그 실행 동안 고정된다. 토글을 누르면 고른 파일은 사라진다. 기존 실행은 한국어다.
- 초기 시험에 쓴 대학 자료 4건(고려대, Dartmouth, 단국대, SUTD)은 외부 전송 승인을 기록하지 않고 지정 엔드포인트로 보냈다.

## 구현 이력

1. 독립 프로젝트, 문서 입력, 역할 추출, 단계별 검토, 자동 진행, 5페이지 화면을 만들었다. 수정안 생성과 수정본 재검토는 이후 제거했다.
2. 논쟁 지점 중심으로 재설계했다. 역할 2~3명 가변, 쟁점 유형 6개, 역할별 독립성, 주의 조항과 의견서.
3. 단일 프롬프트 비교 평가를 추가했다.
4. 실제 모델로 문서 5건을 완주하고 토론 구체성을 고쳤다. 토론은 쟁점별로 입장이 다른 상대 발언에 답한다. 반응 라벨은 수정 전후 거의 같았고 전월세 예시의 발언 내용은 구체화되었다.
5. 서버 자료, 도구, 에이전트 루프를 추가했다.
6. 전체 데이터를 수집하고 평가 명령과 호출 기록을 추가했다.
7. 첫 화면 오른쪽 위에 한국어/English 슬라이드 전환을 추가했다. 선택한 언어는 `ReviewRun.language`에 저장되고 1~5쪽 화면, 의견서, 비교, 에이전트 출력(`prompts/lang_en.md`, `baseline_en.md`)이 그 언어를 따른다. UI 문구는 Django gettext(`locale/en`)이고, 쟁점 유형·우선순위·입장·반응 값은 한국어로 저장하고 화면에서만 번역한다.
8. 입장 나누기와 쟁점 토론을 턴제로 바꿨다. 독립 입장과 토론이 모델 호출 한 번에 항목 하나씩, 역할이 차례로 돌아가며 올라온다(`TURNS = 3`: 역할당 의견·쟁점·토론 바퀴 최대 3). 독립 입장 턴은 자기 의견만 받고 역할의 첫 턴만 서버 자료 검색부터 한다. 더 낼 것이 없는 턴은 호출 없이 건너뛰고 화면에 말풍선을 만들지 않는다. 3명 기준 단계는 8개에서 20개(호출 최대 20회)가 되었다.
9. 쟁점 토론을 대화로 바꿨다. 쟁점마다 사용자가 고른 역할이 자기에게 불리한 점을 먼저 말하고, 다음 역할은 그 발언에, 셋째 역할은 그 발언과 앞선 답변에 답한다. 토론 턴이 앞선 토론 발언을 `history`로 받고, 서버가 답할 ID(`claim_id`, `reply_id`)를 배정해 빠뜨리면 재시도한다. 고른 역할은 에이전트에게 전달되지 않고 발언 순서만 정한다. 같은 문서의 재생에서 토론 `reason` 평균이 378자에서 128자로, 입장 나누기는 246자에서 85자로 줄었고 반응은 수용 편중(답변 6개 중 5개)에서 제한 6, 반박 3으로 바뀌었다. 말풍선은 글을 자르지 않고 전문을 보여주며, 1쪽 문서 이름 입력과 2쪽의 근거 펼침·역할 수정을 뺐다.

## 2026-11-08 정책 사실 온톨로지

## 2026-11-11 배포 설정과 온톨로지 제거
배포 전 점검에 따라 운영 설정을 추가했다. `DEBUG`는 `DJANGO_DEBUG=1`일 때만 켜지고, `DJANGO_SECRET_KEY`와 `DJANGO_ALLOWED_HOSTS`는 환경변수를 `.env`보다 먼저 읽는다. DEBUG가 꺼진 상태에서 비밀 키가 없으면 시작하지 않는다. `server/wsgi.py`와 gunicorn, 정적 파일용 whitenoise를 추가했고, HTTPS 프록시 헤더와 Secure 쿠키를 설정했다.

검수된 사실이 0건이던 정책 사실 온톨로지(모델 4개, 구조화 검색, `load_policy_facts`, `evaluate_conditions`, 평가의 `--structured-facts`, 관련 테스트 25개와 문서)를 제거했다. 0012 마이그레이션이 빈 테이블과 `ReviewRun.structured_facts`를 지운다. 같은 커밋에 들어 있던 호출 계측, `--reference-run`, 반환 구간 인용 검사는 유지했다. 이전 구현은 커밋 edee4b5에 있다. 호출되지 않던 온통청년 조회 함수와 `YOUTH_POLICY_KEY`도 지웠다.

테스트 96개 통과. 로컬 DB에 0012를 적용한 뒤 실행 6건과 서버 자료 67건이 남은 것을 확인했다. DEBUG를 끄고 gunicorn으로 띄워 정적 파일 응답, Secure 쿠키, 비밀 키 누락 시 시작 거부, 디버그 정보 없는 404를 확인했다. HTTPS 프록시 헤더가 있는 POST는 CSRF를 통과하고 헤더가 없거나 허용하지 않은 도메인이면 거부되는 것도 확인했다. 실제 배포 플랫폼에서는 확인하지 않았다.

## 2026-11-11 VibeHub 배포
배포 대상을 VibeHub(git push → GitLab CI 이미지 빌드 → `<app-id>.ai.hy.miwork.ai`)로 정했다. 루트 `Dockerfile`은 python 3.11 이미지에서 정적 파일을 모으고, 시작할 때 `migrate`와 `load_sources`를 실행한 뒤 waitress로 3000 포트에서 받는다. waitress에는 요청 시간 제한이 없어 모델을 기다리는 단계가 서버 쪽에서 끊기지 않는다. `.dockerignore`는 `.env`가 이미지에 들어가지 않게 막는다.

- **DB:** `DB_DATABASE_URL`이 있으면 VibeHub PostgreSQL(연결 prefix `DB`, 수업 자료의 이름)을 쓰고, 없으면 지금처럼 SQLite를 쓴다. 단계 진행은 모델 호출 동안 트랜잭션을 잡고 있어 SQLite에서는 다른 사용자의 쓰기가 5초 뒤 실패하지만, PostgreSQL에서는 그 실행의 행만 잠긴다. `psycopg[binary]`를 추가했다.
- **NUL 문자:** PostgreSQL은 텍스트와 JSON에 NUL을 저장하지 못하는데, PDF에서 뽑은 서버 자료에 NUL이 있어 `load_sources`가 실패했다. `create_run`과 `load_sources`에서 NUL을 지운다. 인용 비교의 `clean()`은 원래 NUL을 무시하므로 검증 결과는 같다.
- **모델 키:** `OPENAI_*`가 없으면 VibeHub가 주입하는 `MINIAPP_LLM_API_KEY`와 `MINIAPP_LLM_BASE_URL`을 쓴다.
- **CSRF:** `CSRF_TRUSTED_ORIGINS`를 `DJANGO_ALLOWED_HOSTS`의 https 주소로 채웠다. 프록시가 `X-Forwarded-Proto`를 빼도 같은 사이트의 POST가 통과한다. 이전 기록의 "헤더가 없으면 거부"는 이제 성립하지 않는다. 토큰과 Origin 검사는 그대로다.
- **서버 자료:** 검수를 통과한 40개 파일(문서 목록, 의견 목록, 통과 문서 38건의 `pages.json`)만 `git add -f`로 저장소에 넣었다. 검수 목록에 없는 평가 문서 등 33건은 넣지 않았다.

테스트 98개가 SQLite와 로컬 PostgreSQL 16 양쪽에서 통과했다. PostgreSQL에 마이그레이션 0001~0012를 적용하고 서버 자료 67건(정책 34, 의견 33)을 적재했다. 컨테이너 시작 명령을 로컬에서 그대로 실행해 다른 Host 헤더의 `/` 응답 200(준비 상태 확인), 정적 파일 200, Secure CSRF 쿠키, 프록시 헤더가 있을 때와 없을 때 POST 통과, 다른 출처와 토큰 없는 POST 거부를 확인했다. Docker가 없어 이미지 빌드는 하지 않았고, VibeHub 배포, VibeHub 모델 엔드포인트 호출, 프록시의 시간 제한과 업로드 크기 제한은 확인하지 않았다.

## 2026-11-11 사회자 토론과 페르소나 (debate_test 브랜치)

손으로 그린 구조도에 맞춰 토론을 바꿨다.

- **페르소나:** `Persona` 테이블과 `load_personas` 명령을 추가했다. Hugging Face 행 API로 NVIDIA Nemotron-Personas-Korea(100만 명, CC BY 4.0)의 무작위 표본 3,000명을 받는다. 역할은 계속 문서에서 뽑고, 역할 추출이 함께 낸 `persona_hint`(나이 범위와 낱말)로 서버가 인물을 골라 `ReviewRun.personas`에 저장한다. 사용자에게는 인물을 보여주지 않고 2쪽에 데이터 출처만 표시한다. 인물 이름은 고를 때 서버가 문장에서 지운 뒤 저장하고(표본 3,000명 전체에서 이름이 남지 않음을 확인), 모델에 보낼 때도 다시 지워 이름이 저장된 이전 실행에서도 보내지 않는다. 발언·쟁점·사회자·최종 정리의 문장에 "○○ 씨" 같은 사람 이름이 있으면 서버가 거부하고 한 번 다시 쓰게 한다(문서 자체에 있는 이름은 허용). 이름 삭제 전 실행 2건에서 토론 발언에 "서준수 씨처럼"이 실제로 나왔고 이것이 이 검사를 넣은 이유다. 나이·지역·직업 같은 구체 정보는 문장에 쓰지 말라고 지시하지만 서버가 막지는 않는다. 행 API는 502, 503, 429를 간헐적으로 내서 재시도와 1초 간격을 두었다. 실제 표본에서 서울·혼자 거주·미혼 → 29세 노원구 미혼 1인 가구, 서울·행정 사무원 → 서초구 공공행정 사무원으로 맞게 골랐다. 데이터에 없는 칸(월세 여부, 소득)은 고를 수 없다.
- **독립 입장 단계 삭제:** 3쪽은 쟁점 정리 한 번이다(`prompts/independent.md` 삭제). 쟁점 정리는 문서와 역할 카드만 본다.
- **사회자:** 쟁점은 정리된 순서대로, 쟁점마다 발언 3개(`PER_ISSUE`)로 다룬다. 쟁점마다 첫 발언은 사용자가 고른 역할이 한다(호출 없이 서버가 배정). 그 뒤 매 차례 사회자 호출(`prompts/moderator.md`)이 다음 발언자, 질문, 새 쟁점을 정하고 이어서 그 역할의 발언 호출이 한 요청 안에서 실행된다. 사회자가 추가한 새 쟁점은 원래 쟁점 뒤에 같은 방식으로 다룬다. 서버는 쟁점 순서, 쟁점별 발언 수, 쟁점 처음 3개와 추가 2개, 직전 발언자 연속 금지, 새 쟁점 원문 인용을 강제하고 어기면 수정 재호출 1회를 한다. 모든 쟁점이 끝나면 호출 없이 `close` 단계를 남기고 5쪽 주의 조항 정리로 넘어간다. 발언자가 답할 상대 발언은 같은 쟁점의 다른 역할 발언에서 서버가 정한다.
- **배정 ID 자동 연결:** 발언 에이전트가 서버가 배정한 쟁점이나 상대 발언 ID를 `target_ids`에서 빠뜨리면, 전에는 수정 재호출 뒤에도 빠질 때 토론이 멈췄다(실제 8번 실행, 세 번째 쟁점 첫 발언에서 "배정된 쟁점과 상대 주장 모두에 답해야 합니다: s1-i3"). 이제 서버가 배정한 ID를 직접 채워 넣고 이 검사는 없앴다. 추가 호출은 없다. ID는 연결 정보일 뿐이고 발언이 그 주장에 실제로 답했는지는 전에도 검증하지 않았다.
- **서버 자료:** 역할의 첫 발언과 최종 정리는 검색을 먼저 하고, 이후 발언은 필요할 때만, 사회자와 쟁점 정리는 검색하지 않는다.
- **3쪽 화면:** 채팅을 없애고 쟁점 카드마다 역할별 한 줄 입장(입론)을 붙였다. 입장은 쟁점 정리 호출이 `positions`로 함께 쓰며(추가 호출 없음), 서버가 모든 역할이 정확히 한 줄씩 썼는지 검증한다. 한 모델이 모든 역할의 입장을 대신 쓰므로 역할 에이전트 각자의 말은 아니다.
- **4쪽 화면:** 채팅 위에 지금 토론 중인 쟁점(번호와 제목)을 띄우고 발언마다 갱신한다. 다룰 쟁점이 바뀌는 발언 앞에 구분선을 넣는다. 사회자가 추가한 새 쟁점은 사회자 말풍선에는 제목만 두고, 채팅 아래 '사회자가 정리한 새 쟁점'에 이유, 입장 차이, 근거를 모은다. 새 쟁점 번호는 처음 쟁점 뒤로 이어 붙인다.
- **해석 차이 중심:** 쟁점 정리는 같은 문구를 역할마다 다르게 읽어 누군가 불리해지는 조항을 먼저 고르고, `contested`와 역할별 한 줄 입장에 각 역할의 읽기를 쓴다. 쟁점의 첫 발언도 그 문구를 어떻게 읽는지와 다르게 읽히면 무엇을 잃는지 밝힌다. 5쪽 주의 조항은 사용자에게 불리하면서 해석이 갈리는 조항을 우선하고, 이전의 `others_view` 대신 `my_reading`(내 해석), `other_role`(다르게 읽는 역할, 사용자 역할을 뺀 이름 중 하나로 스키마가 제한), `other_reading`(그 역할의 해석)을 나란히 보여준다. 이전 실행의 카드는 `others_view`를 불확실한 부분 칸에 그대로 보여준다. 실제 실행에서 두 해석이 각자의 요구사항처럼 나오고 "~라고 읽어요"가 반복되어, 뜻이 갈리는 표현 `phrase`(인용 원문 안의 구절이어야 하며 아니면 서버가 거부)를 추가하고 두 해석을 '그 표현의 뜻 한 문장 + 그 뜻이면 사용자에게 생기는 일 한 문장'으로 쓰게 했다. 실제 모델로 다시 확인하지는 않았다.
- **A/B 비교 형식:** 단일 프롬프트는 그대로 한 문장으로 묻고 답을 원문대로 저장한다. 화면에는 호출 1회(`prompts/baseline_format.md`)를 더 써서 그 답을 PolicyLens 주의 조항과 같은 칸으로 옮긴 `ReviewRun.baseline_items`를 같은 줄 형식으로 보여준다. 옮기는 호출은 답변만 받고 문서는 받지 않으며, 답변에 없는 칸은 비워 화면에서 뺀다. 옮긴 결과는 검증하지 않으므로 옮기는 과정에서 내용이 바뀌었는지는 확인할 수 없다. 평가 명령의 `score`는 계속 원래 답변을 쓴다. 비교 호출은 1회에서 2회가 되었다.
- **호출 수:** 쟁점 하나에 3회 + 사회자 2회로 5회다. 쟁점 3개면 검토 호출은 쟁점 정리 1 + 15 + 최종 1로 17회이고, 새 쟁점 2개가 더해지면 27회다(분석과 검색 제외).

검증: Django 테스트 126개 중 125개 통과. 남은 1개(`test_evaluate_saves_a_time_limited_run_and_leaves_no_row`)는 변경 전부터 Windows 심볼릭 링크 권한(WinError 1314) 때문에 실패하며, 링크 대신 복사로 바꿔 한 번 돌렸을 때는 통과했다(테스트 파일은 원래대로 둠). 마이그레이션 0012 적용, 옛 방식으로 토론 중 멈춘 실행의 1~5쪽이 200으로 열리는 것을 확인했다.

한계:
- **실제 모델로 돌려보지 않았다.** 사회자가 발언자를 고르는 품질, 새 쟁점의 질, 페르소나 구체 정보가 새는지, 호출 시간과 비용은 측정 전이다. 모의 응답 테스트만 있다. (이름 누출은 이름 삭제 전 실행에서 확인되어 위처럼 막았다.)
- 사회자 결정 뒤 발언 호출이 실패하면 결정은 저장되지 않고, 재시작 때 사회자를 다시 부른다.
- 쟁점마다 발언 수가 고정이라 이미 결론이 난 쟁점도 정해진 수만큼 이어진다. (2026-11-13에 사회자가 닫는 방식으로 바뀜)
- 페르소나 매칭은 낱말 포함 여부를 세는 방식이라 거칠다. 맞는 사람이 없으면 페르소나 없이 진행한다.
- 이전 방식의 실행은 이어갈 수 없다. 토론 도중 실행은 재시작하면 오류가 나고, 독립 입장 도중 실행은 더 진행하지 않는다. 끝난 실행의 표시는 그대로다.
- 평가 표(위)의 수치는 이전 구조의 결과다.

## 2026-11-13 관련성 표시, 역할별 이해, 사회자가 닫는 토론, 쟁점 메모 (debate_test 브랜치)

이전 사회자 실행 5건(4~8번)의 토론 발언 44개가 모두 '제한'이었고, 요청은 역할과 관계없이 "기준·결과 공개와 이의 제기 절차"로 모였다. 집행기관 역할도 같은 공개 요청을 했다. 이 관찰에 맞춰 다음을 바꿨다.

- **관련 낮음:** 쟁점 정리가 쟁점마다 `low_relevance`(조항이 goal과 red_line에 직접 닿지 않는 역할 번호)를 낸다. 그 역할의 한 줄 입장은 주장 대신 관련이 낮은 이유를 쓰고 3쪽 카드에 '관련 낮음'으로 표시한다. 서버는 쟁점마다 직접 관련 역할이 둘 이상인지 확인하고, 사회자가 관련 낮은 역할을 발언자로 고르면 거부한다. 사용자 역할이 관련 낮음이면 직접 관련된 첫 역할이 쟁점을 연다.
- **역할별 이해:** 분석 프롬프트가 goal과 red_line을 공정성·투명성 같은 일반 가치가 아니라 돈, 자격, 기한, 업무량, 재량, 책임 범위로 쓰게 하고, 집행기관은 자기 제약에서 찾게 했다. 발언에 `stake`(이 발언이 지키려는 goal이나 red_line) 칸을 추가해 4쪽 말풍선에 '지키려는 것'으로 보인다. 토론 프롬프트는 red_line을 넘는 요구는 반박, goal에 걸리지 않으면 수용으로 하고, 공통 공개 요구로 모이거나 앞사람의 요청을 되풀이하지 않게 했다. 사회자는 모두 같은 요구로 모이면 누가 무엇을 잃는지 묻는다.
- **사회자가 닫는 토론:** 쟁점별 발언 3개(`PER_ISSUE`)를 없앴다. 사회자 응답에 `close`가 생겼고, 새 근거·손실·조건이 더 나오지 않으면 쟁점을 닫는다. 직접 관련 역할이 모두 한 번씩 말하기 전에는 서버가 닫기를 거부한다. 닫으면 호출 결과를 `issue_close` 단계로 남긴다. 사회자가 닫지 않는 경우를 막기 위해 쟁점당 발언 10개(`MAX_STATEMENTS`)에서 서버가 다음 쟁점으로 넘긴다. 쟁점 하나는 이제 발언 수 n에 대해 2n회 호출이다(여는 발언 1, 이후 발언마다 사회자와 발언 2, 닫는 사회자 1).
- **쟁점 메모:** 사회자 응답의 `new_issues`(원래 쟁점 뒤에 토론)를 없애고, 사회자만 쓰는 `note_issue` 도구와 `IssueNote` 테이블(마이그레이션 0014)을 추가했다. 메모는 원문 인용을 서버가 대조하고 같은 조항은 다시 남기지 않는다. 메모는 토론하지 않으며, 그 단계가 저장될 때만 함께 저장해 실패하거나 다시 시도한 차례의 메모는 남지 않는다. 4쪽 채팅 아래 '사회자의 쟁점 메모'에 모이고, 최종 정리에 `noted_issues`로 전달되어 토론하지 않은 메모 쟁점임을 밝히게 했다. 사회자는 서버 자료를 검색하지 않는다는 규칙은 그대로다. 이전 실행에 저장된 `new_issues`는 계속 표시된다.

검증: Django 테스트 131개 중 130개 통과. 남은 1개(`test_evaluate_saves_a_time_limited_run_and_leaves_no_row`)는 이전 기록과 같은 Windows 심볼릭 링크 권한(WinError 1314) 실패다. 새 테스트는 관련 낮은 역할 제외와 닫기 조건 검증, 사용자 역할이 관련 낮을 때 여는 역할, 사회자가 닫는 시점, 안전 상한, 메모 저장·거부·중복·표시·최종 전달, 이전 실행의 새 쟁점 표시를 확인한다. 영어 번역 13개를 추가하고 `.mo`를 다시 만들었다.

한계:
- **실제 모델로 돌려보지 않았다.** '제한' 쏠림과 공개 요청 수렴이 줄었는지, 사회자가 너무 일찍 또는 늦게 닫는지, 관련 낮음 판단이 맞는지, 메모 품질은 모의 응답으로만 확인했다.
- 발언 수가 실행마다 달라져 실행 간 비용과 결과 비교가 이전처럼 고정되지 않는다.
- `stake`가 실제 goal이나 red_line과 맞는지는 서버가 검사하지 않는다.

### 같은 날 수정: 관련 낮음 기준 완화와 조건부 호출

11번 실행(지출효율화 TF 기사)에서 쟁점 2 '참여예산 선정기준'의 청년 참여단(사용자 역할)이 관련 낮음으로 표시됐다. 그 역할의 goal은 "청년정책 아이디어가 예산사업 검토에 반영"이라 선정기준에 직접 닿고, 모델이 쓴 한 줄 입장도 실제 이해("다른 사업과 경쟁할 때 적용될 공개 기준")를 주장해 표시와 어긋났다. 모델이 '조항의 직접 대상인가'로 판단한 것으로 보이며 프롬프트의 "간접 영향만 있으면 관련이 낮다"가 이를 부추겼을 수 있다.

- 쟁점 정리 프롬프트: 입장을 지어내야만 하는 역할만 관련 낮음으로 표시한다. 예산이나 기회를 나눠 갖거나 비용, 업무, 위험이 옮겨 오면 관련이 있고, 얻거나 잃는 것을 구체적으로 쓸 수 있거나 판단이 애매하면 표시하지 않는다.
- 조건부 호출: 사회자 응답에 `shifted_by`(이 쟁점의 발언 ID 또는 none, 스키마 enum)를 추가했다. 관련 낮은 역할은 같은 쟁점에서 다른 역할이 한 발언을 `shifted_by`로 지목할 때만 부를 수 있고, 질문에 그 발언자와 옮겨 오는 것을 밝힌다. 서버는 지목한 발언이 이 쟁점의 다른 역할 발언인지 확인한다. 불린 역할은 그 발언으로 떠안는 것만 말한다. 지목한 ID는 사회자 결정에 저장한다.

검증: 테스트 132개 중 131개 통과(같은 심볼릭 링크 실패 1개). 11번 문서로 쟁점 정리를 다시 돌려 판단이 바뀌는지는 확인하지 않았다.

### 같은 날 추가: 사용자가 쟁점 넘기기

4쪽 '지금 토론 중인 쟁점' 줄에 '다음 쟁점으로' 버튼을 넣었다(마지막 쟁점은 '토론 마치기'). 지금 쟁점에 발언이 3개(`MIN_BEFORE_SKIP`) 이상일 때만 보이고, `/reviews/<id>/skip/`가 모델 호출 없이 `issue_close` 단계를 `by: user`로 남긴다. 사회자가 닫은 단계는 `by: moderator`다. 단계 진행과 같은 커서·스냅샷 확인을 써서 지난 커서는 409, 발언이 모자라면 400이다. 발언을 만드는 중에 누르면 버튼이 '이번 발언이 끝나면 넘어가요'로 바뀌고 그 발언이 끝난 뒤 넘긴다. 최종 정리 프롬프트는 사용자가 넘긴 쟁점의 다른 역할 해석을 실제로 나온 발언에서만 쓰고 나머지는 불확실한 부분에 남기게 했다.

검증: 테스트 133개 중 132개 통과(같은 심볼릭 링크 실패 1개). 발언 2개에서 거부, 3개에서 버튼 표시와 넘기기, 모델 미호출, 지난 커서 거부, 마지막 쟁점의 '토론 마치기'를 확인했다. `review.js`는 문법 검사만 했고 브라우저에서 진행 중 넘기기를 눌러 보지는 않았다.

## 2026-11-13 main 병합 (merge-main 브랜치)

UI/UX 작업을 두 변경 위에서 하기 위해 `debate_test`에서 `merge-main`을 만들고 `origin/main`(597c438, VibeHub 배포·온톨로지 제거·최신 정책 슬라이더)을 합쳤다. 온톨로지는 main을 따라 지웠고(`test_ontology.py`, 모델 4개, `structured_facts`, `policy_facts` 기록), 사회자 토론·페르소나·쟁점 메모는 그대로 두었다. `urls.py`는 양쪽 경로(`latest/`, `skip/`)를 모두 둔다. 두 브랜치의 0012 마이그레이션은 `0015_merge_…`로 합쳤다. 번역은 양쪽 항목을 모두 두고 `.mo`를 다시 만들었다(중복 msgid 없음).

검증: 테스트 111개 중 110개 통과(같은 심볼릭 링크 실패 1개, 온톨로지 테스트가 빠져 개수가 줄었다). 로컬 SQLite에 0012_remove_policy_ontology와 0015를 적용했다. PostgreSQL과 VibeHub 배포에서는 확인하지 않았다.

## 2026-11-13 UI 확인용 더미 모드 (ui-ux 브랜치)

`.env`의 `POLICYLENS_DUMMY=1`이면 `transport.call`이 `server/integrations/dummy.py`의 고정 응답을 돌려주고, 최신 정책 목록도 더미 3건을 쓴다. 모델 제공자와 정책브리핑은 호출하지 않는다. 응답은 올린 문서의 문장을 잘라 인용하므로 서버 검증을 그대로 통과하며, 관련 낮음 표시, 사회자 메모 1건, 사회자가 닫는 쟁점, A/B 비교까지 한 번씩 나온다. 호출마다 0.8초를 쉬어 입력 중 표시와 애니메이션이 실제처럼 보인다. 더미 실행은 제공자가 `dummy`로 저장되어 실제 설정에서는 이어지지 않고, 최신 정책 캐시도 모드별로 나눴다. 요약, 정책 제목 등에 '더미'를 넣어 실제 결과와 구분한다.

검증: 테스트 113개 중 112개 통과(같은 심볼릭 링크 실패 1개). 더미 모드로 문서 입력부터 최종 정리와 A/B 비교까지 네트워크 호출 없이 끝나는 것과, 더미 실행이 실제 설정에서 거부되는 것을 확인했다. 브라우저 화면은 확인하지 않았다.

## 2026-11-14 사용자가 고른 메모 쟁점 토론 (ui-ux 브랜치)

사회자의 쟁점 메모는 기록만 하고 토론하지 않았다. 이제 4쪽 메모 카드에 '이 쟁점도 토론하기' 버튼이 있고, 누른 메모는 원래 쟁점이 끝난 뒤 누른 순서대로 다른 쟁점과 같은 방식(여는 발언, 사회자가 닫기, 사용자 넘기기)으로 토론한다.

- `IssueNote.added_at`(마이그레이션 0016)에 추가한 시각을 저장한다. 서버는 추가된 메모를 `added_issues` 단계로 history 끝에 붙여 사회자, 발언, 최종 정리가 같은 쟁점 목록을 보게 한다. 쟁점 ID는 `note-<번호>`이고 메모 카드가 그 ID를 가진다.
- `/reviews/<id>/notes/<note>/debate/`는 쟁점 넘기기와 같은 커서·스냅샷 확인을 쓴다. 지난 커서는 409, 토론이 닫혔거나 이미 추가한 메모는 400이다. 발언을 만드는 중에 누르면 '이번 발언이 끝나면 추가해요'로 바뀌고 그 발언 뒤에 보낸다.
- 토론 마무리 단계가 저장되면 더 추가할 수 없다. 마지막 쟁점이 닫히면 바로 마무리로 넘어가므로, 메모는 토론이 진행되는 동안 골라야 한다.
- 최종 정리의 `noted_issues`에 `added`를 넣고, 프롬프트는 추가된 메모를 토론한 쟁점으로, 나머지는 토론하지 않은 메모로 다루게 했다. 사회자 프롬프트와 메모 도구 설명도 맞췄다. 영어 번역 4개를 추가하고 1개를 고쳤다.

검증: 테스트 114개 중 113개 통과(같은 심볼릭 링크 실패 1개). 새 테스트는 버튼 표시, 지난 커서 거부, 모델 호출 없는 추가, 중복 거부, 원래 쟁점 뒤 토론 순서와 닫기, 최종 정리 전달, 토론이 닫힌 뒤 버튼이 사라지고 추가가 거부되는 것을 확인한다. ui-ux에서 빠졌던, 테스트가 `.env`의 더미 모드를 끄는 설정을 다시 넣었다. `review.js`는 문법 검사만 했고 브라우저에서 눌러 보지는 않았다. 실제 모델로 추가 메모를 토론해 보지 않았다.

## 2026-11-14 화면 다듬기 (ui-ux 브랜치)

- 대기 화면: 문서 분석(1→2), 쟁점 정리(2→3), 주의 조항 정리(4→5) 동안 문서를 돋보기로 훑는 전체 화면과 2.6초마다 바뀌는 문구를 띄운다(`reading_screen.html`). 문서 분석은 업로드 요청 안에서 돌기 때문에 홈 화면 위에 덮는 방식이며 별도 주소의 페이지는 아니다. 쟁점·주의 조항 단계는 입장 선택이나 '주의 조항 보기'로 넘어온 첫 화면부터 덮고, 단계가 끝나거나 오류가 나면 걷는다. 주의 조항은 완성 화면을 다시 불러올 때까지 유지한다. 움직임 줄이기 설정에서는 애니메이션이 멈춘다.
- 검토 화면에서 단계 표시의 '1 문서 넣기'를 누르면 "그동안 내용이 사라집니다" 확인 창을 띄운다(`dialog`). 로고 링크에는 넣지 않았다.
- 입장 선택 카드는 카드 어디를 눌러도 선택된다. 내 발언과 내 차례 입력 중 표시는 오른쪽 내 아바타 옆에 붙는다.
- 쟁점 넘기기 버튼을 채팅 아래 메신저 입력줄 자리로 옮겼다. 발언 3개 전에는 잠긴 버튼과 "발언 n개 뒤에 다음 쟁점으로 넘어갈 수 있어요"를, 그 뒤에는 켜진 버튼을 보인다.

검증: 테스트 114개 중 113개 통과(같은 심볼릭 링크 실패 1개). 더미 모드로 2→3, 4→5 첫 화면에 대기 화면이 그려지고 끝난 실행에는 없는 것을 확인했다. JS는 문법 검사만 했고 브라우저에서 애니메이션, 확인 창, 버튼을 눌러 보지 않았다.
