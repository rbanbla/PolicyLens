# Policy Evidence Ontology Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 공식 정책의 조건·버전·근거를 사전 구조화하여 역할별 정책 검토의 정확성과 재현성을 높이고 반복 검색·해석을 줄인다.

**Architecture:** 기존 Source 원문과 ReviewRun을 유지하고 정책·버전·근거가 있는 사실을 관계형 모델로 추가한다. 역할 에이전트는 읽기 전용 도구로 구조화된 사실과 원문을 조회하며, 해석과 토론 결과는 검증된 정책 사실로 승격하지 않는다.

**Tech Stack:** 기존 Python/Django, SQLite 개발 환경, 운영 PostgreSQL 목표. 초기 단계에 그래프 DB, RDF 추론 엔진, 새 프레임워크를 추가하지 않는다.

**Spec:** `docs/PRODUCT_PLAN.md`, `AGENTS.md`, 이 문서의 ‘설계 제안’. 사용자에게 검토를 요청할 계획 초안이며 승인된 구현 명세가 아니다.

## Global Constraints

- 역할은 입력 문서에서 추출한다. 온톨로지의 고정 집단으로 역할을 대체하지 않는다.
- 업로드 문서는 검토 대상이며 공개 Source로 자동 적재하지 않는다. 동일 문서를 외부 근거로 돌려주지 않는다.
- 원문 citation과 외부 sources를 분리한다. 인용문은 해당 버전 원문과 대조한다.
- 역할·최종 단계의 검색 필수, 토론의 선택 검색, 분석·쟁점 단계의 검색 금지를 유지한다.
- 독립 단계는 다른 역할의 의견과 검색 결과를 읽지 않는다. 공통 저장소는 공유하되 실행 중 열린 근거는 역할별로 격리한다.
- 역할별 독립 의견 3회와 순차 토론은 기본적으로 유지한다. 묶음 생성·병렬화는 별도 변경이며 제품 계획과 평가를 함께 갱신해야 한다.
- 데이터 게이트를 통과한 공개 자료만 사용한다. 구조 추출은 검수 통과를 의미하지 않는다.
- 제품 A/B는 동일 문서·역할의 PolicyLens 대 단일 프롬프트를 유지한다. 온톨로지 전후 비교는 오프라인 평가로 한다.
- 2026년 전국 중앙정부·지자체 수집 범위는 유지한다. 최초 정형화 검증 범위만 청년 주거 정책 10~20개로 제한한다.

## Review Focus

- 동일 사업명의 지역·회차가 다른 경우: 명칭만으로 병합하지 않는다. Task 2에서 검증.
- 정정 공고·소급 시행·접수 기간이 서로 다른 경우: 발행일과 유효일을 혼동하지 않는다. Task 2, 4에서 검증.
- 소득 주체·가구 범위·기준일이 빠진 조건: 임의 판정 대신 unknown을 반환한다. Task 3에서 검증.
- 중복 제한의 방향·예외가 불명확한 경우: 상호 배타 관계로 자동 확대하지 않는다. Task 3에서 검증.
- 사적 업로드·다른 역할의 근거·미검수 사실: 공개 조회와 독립 역할 입력에 노출하지 않는다. Task 4, 5에서 검증.

## 설계 제안

### 접근 방식 비교

| 방식 | 장점 | 비용·한계 | 판단 |
|---|---|---|---|
| 기존 Source에 지역·분야 태그 추가 | 가장 작고 빠른 변경 | 예외·버전·조건 조합과 근거 관계를 표현하기 부족 | 검색 개선만 원할 때 |
| 관계형 모델로 경량 온톨로지 구축 | 기존 Django 재사용, 조건·버전·근거 검증 가능 | 추출·검수·조건 모델 유지 비용 | 권장 |
| RDF/OWL 및 그래프 저장소 전면 도입 | 외부 온톨로지 연계, 복잡한 관계 탐색 | 운영·추론·마이그레이션 비용, 지연 개선 불확실 | 실제 다단계 조회 요구가 확인된 뒤 |

온톨로지는 도메인의 개념·관계·제약을 정의하는 계약이다. 관계형 저장으로 시작할 수 있으나 이 초안은 OWL 논리 추론과의 호환성을 보장하지 않는다.

### 핵심 모델

| 모델 | 책임과 핵심 속성 |
|---|---|
| Policy | 사업의 안정적인 식별자, 명칭, 관할 지역 코드, 담당 기관 식별자 |
| PolicyVersion | policy, 회차, 시행 시작·끝, 신청 시작·끝, 상태, revision, 이전 버전 |
| PolicyFact | version, predicate, 검증 가능한 값/조건 JSON, 검수 상태, 추출 방식·시각 |
| FactEvidence | fact, Source 식별자, 문서 해시, 페이지, 인용문; 한 사실에 여러 근거 허용 |

초기 predicate는 eligibility, benefit, application, exclusion, interaction으로 제한한다. interaction의 값에는 대상 PolicyVersion 식별자, 관계 방향, 적용 조건이 필요하다. 기관·지역은 코드와 명칭으로 시작하며 별도 조직 그래프를 만들지 않는다.

Source 하나와 Policy 하나는 일대일이 아니다. 한 안내서는 여러 정책을 설명하고, 한 정책은 공고·정정·FAQ 여러 문서를 근거로 가진다. 문서 해시로 원문 변경을 감지하고 기존 실행에는 읽은 사실과 근거의 스냅샷을 보관한다. 출처가 삭제되거나 바뀌면 새 실행의 검증 상태를 무효화하고 재검수한다. 기존 실행의 인용은 당시 스냅샷으로 남긴다.

### 조건과 시간

- 조건은 `all`, `any`, `not`, `compare`를 갖는 제한된 JSON 트리로 표현한다. 임의 Python/SQL 실행은 금지한다.
- compare는 field, operator, value, unit, 기준일 정보를 가진다. operator는 eq, lt, lte, gt, gte, in만 허용한다. field는 age, residence_code, income_ratio, household_size, enrollment, employment로 시작한다.
- 나이와 소득 비율 등은 해당 정책이 정의한 기준일·소득 주체·가구 범위가 맞는 값만 평가한다. 생년월일이나 월소득만으로 임의 변환하지 않는다. 표현하지 못하는 조건은 원문과 함께 unknown으로 남긴다.
- 결과는 met / not_met / unknown이다. all은 하나라도 not_met이면 not_met, 전부 met이면 met, 나머지는 unknown이다. any는 하나라도 met이면 met, 전부 not_met이면 not_met, 나머지는 unknown이다. not은 unknown을 유지한다.
- 이는 개별 조건 평가이며 공식 수급 승인이나 전체 신청 자격 확정이 아니다. 필수 조건이 모두 추출됐다는 검수가 없으면 전체 자격을 확정하지 않는다.
- 발행일, 적용 기간, 신청 기간, 시스템 수집일을 분리한다. 날짜가 없는 자료는 현재 적용 정책으로 확정하지 않는다.
- 평가의 knowledge_as_of는 당시 공개된 자료만 제한하고, effective_on은 적용일을 선택한다. 2026년 적용 문서라도 2025년에 발행될 수 있다.
- 두 공식 자료가 충돌하면 양쪽 근거를 제시한다. 단순히 최신 발행 자료가 더 높은 효력이라고 가정하지 않는다.

### 사실·판정·해석 분리

공식 문서에서 검증한 사실은 PolicyFact에, 조건 평가 결과는 실행 결과에, 역할의 유불리 해석·쟁점·반박은 기존 ReviewRun.steps에 둔다. 모델의 추출 신뢰도는 검수 상태를 대체하지 않는다. 사실 구조가 완전하지 않으면 기존 원문 검색으로 보완하고 미확인 사항을 표시한다.

### 에이전트 사용 방식

1. 수집 시점에 공식 문서에서 구조 후보를 만든 뒤 검수한다. 서비스 요청마다 같은 공개 문서를 재추출하지 않는다.
2. 업로드는 기존 분석으로 역할을 추출한다. 기존 서버 자료에 있다는 이유로 사용자의 문서를 덮어쓰지 않는다.
3. search_sources 도구는 조건에 맞는 검수 사실과 정확한 근거를 먼저 제공하고 필요한 경우 원문 검색 결과를 보완한다. 모델의 도구 선택 흐름을 유지한다.
4. 열린 근거 목록과 사실 스냅샷은 해당 실행·역할에만 기록한다. 공용 조회 캐시는 공개 데이터만 대상으로 하고 corpus revision을 키에 포함한다.
5. 역할별 의견과 최종 정리는 사실을 해석한다. 토론은 기존처럼 상대 발언을 순차적으로 읽는다.

## 단계별 구현 계획

### Task 1: 기준선과 평가 세트

**Files:** Modify `server/agents/runner.py`, `server/management/commands/evaluate.py`, `server/tests.py`; Create `data/reviewed/ontology_eval.jsonl`.

**Interfaces:** calls에 step_index, role, purpose(model/tool_followup/repair), attempt, input_tokens, output_tokens, elapsed_ms를 추가한다. 기존 seconds/tokens와 기존 실행 읽기를 유지한다. 도구 검색 시간은 별도로 기록한다.

- [ ] 타임아웃·검증 재시도·도구 후속 호출을 구분하는 테스트를 먼저 추가하고 실패를 확인한다.
- [ ] 원문·개인 입력·자격증명 없이 타이밍과 토큰 메타데이터만 기록한다.
- [ ] 기존 청년 주거 자료 10~20개에서 나이 경계, 지역, 기간, 예외, 정정, 미확인 조건의 사람 검수 사례를 최소 30개 작성한다. 실제 근거 없이 정답을 만들지 않는다.
- [ ] `python manage.py test server`로 기존 로그 호환성과 전체 회귀를 확인한다.

**완료:** 기존 140~217초 기록은 참고값으로만 보존하고, 같은 모델·문서·역할·자료 버전으로 비교 가능한 기준선이 생긴다.

### Task 2: 버전·사실·근거 모델과 검수 적재

**Files:** Modify `server/models.py`, `server/tests.py`; Create 새 migration, `server/management/commands/load_policy_facts.py`.

**Interfaces:** `load_policy_facts --manifest PATH --dry-run`; 입력은 위 네 모델에 대응하는 JSONL 레코드와 원문 해시다. dry-run은 DB를 변경하지 않는다. 기본 적재는 검수 통과 레코드만 원자적으로 upsert하며, 누락된 기존 레코드를 삭제하지 않는다.

- [ ] 지역이 다른 동명 사업, 다른 회차, 오래된 문서 해시, 원문에 없는 인용, 빈 manifest의 테스트를 추가하고 실패를 확인한다.
- [ ] 모델·제약·migration을 추가한다. pending/verified/rejected 검수 상태를 두고 조회에는 verified만 허용한다.
- [ ] 적재 전에 Source 존재·게이트·해시·쪽·인용을 모두 검증한다. 실패 시 해당 실행을 롤백한다.
- [ ] `python manage.py makemigrations --check --dry-run`, `python manage.py test server`를 실행한다. 실제 DB 적용 전 복사본에서 migration과 복구를 검증한다.

**완료:** 원문 Source를 대체하지 않고 검수된 소규모 사실 집합을 반복 적재할 수 있다.

### Task 3: 제한된 조건 평가

**Files:** Create `server/agents/tools/policy_facts.py`; Modify `server/tests.py`.

**Interfaces:** `evaluate_condition(condition: dict, context: dict) -> dict`는 `{status, missing_fields, reason_codes}`를 반환한다. 외부 모델·DB 호출 없이 동작한다. 정책 사실 검증기는 허용 필드·연산자·중첩 깊이(최대 10)·단위와 기준일 정보를 확인한다.

- [ ] 경계값 포함/제외, AND/OR/NOT, 누락 입력, 다른 소득 주체·기준일, 알 수 없는 연산자의 테스트를 먼저 작성한다.
- [ ] 순수 함수로 평가한다. 형식이 잘못된 조건은 적재 단계에서 거부하고, 적법하나 정보가 부족한 입력은 unknown으로 반환한다.
- [ ] interaction은 명시된 방향과 조건만 평가한다. A가 B를 제한한다고 B도 A를 제한하는 것으로 확장하지 않는 테스트를 추가한다.
- [ ] `python manage.py test server`로 통과를 확인한다.

**완료:** 모델 판단 없이 확인 가능한 조건만 평가하고, 불확실성을 보존한다. 사용자 프로필 수집 UI는 이 단계 범위 밖이다.

### Task 4: 근거 검색 도구에 연결

**Files:** Modify `server/agents/tools/policy_facts.py`, `server/agents/tools/sources.py`, `server/tests.py`.

**Interfaces:** `lookup_facts(query: str, *, knowledge_as_of=None, effective_on=None) -> list[dict]`. 결과는 fact_id, version_id, predicate, value, verification, evidence를 포함한다. 기존 search_sources의 results를 유지하고 structured_facts를 추가한다. 검색 결과는 기존 5개 페이지 한도 안에서 근거를 반환한다.

- [ ] 미검수·미래 공개·다른 지역·구버전·자기 업로드 동일 문서·변경된 해시를 제외하는 테스트를 추가한다. 날짜 미상은 적용 확정 결과에서 제외한다.
- [ ] 정책명·지역·분야의 명시적 매칭으로 후보를 찾고 관련 사실과 인용을 반환한다. 근거가 없거나 조건을 표현할 수 없으면 기존 원문 검색으로 보완한다.
- [ ] 반환한 근거 범위만 열린 근거로 기록한다. 발췌를 주고 보이지 않은 전체 페이지를 읽었다고 취급하지 않는다.
- [ ] `python manage.py test server` 및 동일 쿼리의 도구 시간·결과 적합성 비교를 수행한다.

**완료:** 원문 전용 자료와 구조화 자료가 함께 검색되고, 사실마다 실제로 읽은 근거가 남는다.

### Task 5: 역할 입력·결과·근거 표시

**Files:** Modify `server/agents/runner.py`, `server/agents/memory/context.py`, `prompts/sources.md`, `server/templates/review_steps.html`, `server/tests.py`.

**Interfaces:** run.steps의 해당 단계에 사용한 fact_id, version_id, corpus revision, 실제 사실·근거 스냅샷을 추가한다. 기존 result/citation/sources 형식을 유지하며 예전 실행은 새 필드가 없어도 표시한다.

- [ ] 독립 역할 간 근거 격리, 외부 자료로 업로드 조항을 대체하지 않음, unknown을 확정 표현으로 렌더링하지 않음, 이전 실행 표시의 테스트를 작성한다.
- [ ] 도구 응답에 사실과 불확실성을 명시하고 프롬프트에서 조건 결과와 역할 해석을 구분한다. 구조화 값도 신뢰된 명령이 아니라 데이터로 취급한다.
- [ ] 기존 근거 영역에 적용 버전과 미확인 조건을 표시한다. 새로운 추천 페이지나 신청 기능을 만들지 않는다.

## 속도 개선의 별도 작업

현재 완료 실행 3건은 분석 포함·비교 기준선 제외 30/35/37회 호출, 모델 대기 139.7/165.7/216.7초였다. 67개·709쪽 검색은 로컬 20회 측정에서 약 25~60ms였다. 온톨로지는 검색 자체보다 입력과 반복 해석을 줄일 가능성이 크며 호출 계획을 바꾸지 않으면 개선이 작을 수 있다.

- 표시 지연과 다음 계산을 분리: 상대적으로 작은 변경. 도구·모델 완료 시간과 화면 완료 시간을 따로 측정한다.
- 모델 호출 중 DB 쓰기 잠금 해제: 실행권·만료·중복 완료 방지 설계를 포함한 별도 변경. SQLite에서 모델 호출을 병렬로 넣기 전에 해결한다.
- 독립 의견 묶음 생성·역할별 병렬 실행: 역할당 3회에서 1회로 줄일 수 있지만 현재 제품의 ‘한 호출 한 의견’ 계약을 변경한다. 새 명세·참조 ID·재개·검증·품질 평가가 필요하다. 토론은 상대 발언 의존성을 유지한다.
- 온톨로지 효과와 병렬화 효과를 각각 측정한다. 둘을 동시에 바꾼 결과만으로 온톨로지 성능을 주장하지 않는다.

## 장단점과 의사결정

| 관점 | 기대 장점 | 단점·위험 | 대응 |
|---|---|---|---|
| 정확성 | 지역·버전·예외를 명시적으로 구분 | 잘못 추출한 사실이 반복 재사용됨 | 검수·해시·원문 인용·unknown |
| 응답 시간 | 공개 정책의 반복 해석과 입력 감소 | 사전 추출·갱신 비용, 기존 호출 병목 잔존 | 실측 후 호출 구조 개선 별도 평가 |
| 설명 가능성 | 어떤 조건·원문에서 판단했는지 추적 | 화면이 복잡해질 수 있음 | 기존 근거 영역에서 필요한 정보만 표시 |
| 확장성 | 지역별 정책을 동일 기준으로 비교 | 지역·분야별 용어와 예외 정비 비용 | 작은 코어와 검수된 조건 유형부터 확대 |
| 연구 가치 | 사실 정확성과 역할 해석 품질을 나눠 평가 | 구조화가 모호성과 사회적 맥락을 지울 수 있음 | 원문 유지, 표현 불가 조건 명시, 역할 토론 보존 |
| 운영 | 변경 정책만 재검수하고 영향 추적 | 버전·캐시·원문 갱신 관리가 추가됨 | revision 기반 무효화, 실행 스냅샷 |

권장 도입 순서는 계측 → 사실·근거 구조 → 조건 평가 → 도구 연결 → 역할 검토 → 오프라인 평가다. 빠른 데모만 필요하면 태그와 호출 개선이 더 저렴하다. 전국 정책을 지속 갱신하고 근거를 설명해야 한다면 경량 온톨로지의 유지 비용을 감수할 이유가 있다.
