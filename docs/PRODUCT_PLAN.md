# PolicyLens v2 제품 및 구현 계획

## 과제 요구
Topic 6, Development of Stakeholder Agent Related to Policy Documents. 정책 문서에 피드백을 제출할 수 있는 이해관계자 에이전트, 이해관계자 추출 요구사항 도출, 입장 제시와 토론 환경, 사회적으로 중요한 주제의 국내외 정책 데이터를 요구한다.

## 목적과 가정
정책 문서가 내 입장에 미치는 영향을 이해하고 주의할 조항을 찾는 서비스다. 정책 문구는 사용자가 바꾸기 어려우므로 수정안을 만들지 않는다. 입력은 공공정책 문서이며 부동산, 세금, 청년 등 주제는 코드에 고정하지 않는다. 대부분의 조항은 자명하므로 논쟁 지점을 찾아 그곳만 토론한다. 로컬 SQLite를 사용하며 운영 DB 목표는 PostgreSQL이다.

## 다섯 페이지
1. 정책 문서를 입력한다.
2. 문서 유형, 정책 분야, 목적, 적용 대상, 요약과 대표 이해관계자 2~3명을 제시한다. 역할마다 그 역할을 대신 말할 가상 인물(페르소나)을 붙이되, 사용자에게는 인물의 이름과 구체 정보를 보여주지 않고 데이터 출처만 표시한다. 사용자가 역할을 확인하고 자신의 입장을 고른다. 문서에 직접 언급되지 않은 역할은 그 사실을 표시한다.
3. 문서와 역할 카드(페르소나 포함)로 토론할 쟁점을 최대 3개 고르고, 쟁점 카드마다 역할별 한 줄 입장(입론)을 붙여 보여준다. 채팅이 아니며, 쟁점과 입장은 쟁점 정리 호출 한 번이 함께 쓴다. 제외한 내용도 함께 보여준다. 역할별 독립 입장 단계는 없다.
4. 사회자 에이전트가 진행하는 쟁점 토론이다. 쟁점은 정리된 순서대로 하나씩 다루고, 쟁점마다 발언 수가 정해져 있다(3개). 쟁점마다 첫 발언은 사용자가 고른 역할이 자기에게 불리한 점을 말한다. 그 뒤로는 사회자가 매 차례 다음 발언자와 그 발언자에게 던질 질문을 정하고, 토론에서 새로 부딪힌 조항을 쟁점으로 추가한다(최대 2개, 원래 쟁점 뒤에 같은 방식으로 다룸). 발언자는 같은 쟁점의 앞선 발언에 수용·제한·반박으로 답한다. 쟁점 순서, 쟁점별 발언 수, 쟁점 수, 직전 발언자의 연속 발언 금지는 서버가 강제하고, 모든 쟁점이 끝나면 토론을 마친다. 화면은 채팅 위에 지금 토론 중인 쟁점을 띄우고 쟁점이 바뀌는 곳에 구분선을 넣으며, 사회자가 추가한 새 쟁점은 채팅 아래 '사회자가 정리한 새 쟁점'에 따로 모은다. 고른 역할은 에이전트와 사회자에게 정보로 전달되지 않고 쟁점마다 첫 발언자만 정한다. 발언에는 사람 이름이나 페르소나의 구체 정보가 나오지 않는다.
5. 내 입장에서 주의할 조항을 보여준다. 나에게 불리할 수 있으면서 다른 역할이 같은 문구를 다르게 읽는 조항을 먼저 고른다. 해당 조항, 내게 미치는 영향, 쟁점 유형, 뜻이 갈리는 표현(조항 원문 그대로), 그 표현에 대한 내 해석과 가장 다르게 보는 다른 역할의 해석(역할 이름과 함께, 각각 뜻과 그 뜻일 때 내게 생기는 일), 확인할 것, 담당 기관에 물어볼 질문, 불확실한 부분을 포함한다. 역할별 의견서를 함께 제공한다. 법률·세무 자문이 아니라는 안내를 표시한다.

## 이해관계자 추출 요구사항
1. 포함: 문서가 권리·의무·혜택·부담·결정권을 배분하거나 그 결과를 직접 받는 집단이다.
2. 대표 선정: 이해가 서로 다른 집단 2~3개. 동의어는 함께 고르지 않는다. 같은 집단이라도 조항이 조건에 따라 다른 결과를 주면 사용자가 미리 자기 위치를 알 수 있는 조건 하나로 나누되, 집행기관이나 결정권자의 자리는 남긴다. 결과가 갈리지 않는 하위 분류는 함께 고르지 않고 나머지는 기타 이해관계자로 기록한다.
3. 다양성: 가능하면 수혜자·부담자·집행자를 섞는다. 고정된 이름을 강제하지 않는다.
4. 근거 유형: 문서에 언급된 explicit과, 언급은 없지만 조항의 효과가 직접 미치는 implied를 구분한다. 둘 다 원문 조항을 인용한다.
5. 근거 부족: 둘 이상 찾지 못하면 역할을 지어내지 않고 이유를 안내한다.
6. 페르소나: 역할은 문서에서 뽑고, 역할 추출이 함께 낸 조건(나이 범위와 낱말)으로 NVIDIA Nemotron-Personas-Korea(CC BY 4.0) 표본에서 인물 한 명을 고른다. 나이와 낱말이 하나 이상 맞는 사람이 없으면 붙이지 않고, 한 인물을 두 역할에 쓰지 않는다. 페르소나는 합성 인물이라 발언의 처지를 구체화하는 데만 쓰고 근거로 쓰지 않는다. 인물 이름은 서버가 고를 때 지워서 저장하고 모델에게도 보내지 않으며, 나이·지역·직업 같은 구체 정보는 에이전트가 화면 문장에 쓰지 않도록 지시한다.

## 쟁점 판별
같은 문구를 역할마다 다르게 읽을 수 있고, 어떻게 읽느냐에 따라 어느 역할이 불리해지는 조항을 먼저 쟁점으로 고른다. 쟁점 정리는 사용자의 역할을 모르므로 누구에게 불리한지는 열어 두고, 5쪽에서 사용자 역할 기준으로 다시 고른다.
주제가 아니라 조항의 구조로 판별한다. 이해 충돌, 모호성, 재량 집중, 경계·배제, 부담 전가, 누락의 여섯 유형이다. 어디에도 해당하지 않는 정의, 시행일, 단순 절차는 제외하고 제외 내용을 기록한다. 누락 지적은 관련 조항을 인용하되 문서에 없는 내용임을 밝힌다.

## 검토 원칙
언급 횟수나 다수결로 쟁점이나 편향을 확정하지 않는다. 서버는 원문 인용, 서버 자료 인용, 참조 범위를 검증한다. 역할 에이전트는 자기 카드만 받고 사용자의 선택은 최종 단계에만 전달해 독립성을 지킨다. 역할들의 일치는 사실 검증이 아니다. 판단할 수 없는 사항은 질문과 불확실성으로 남긴다.

## 서버 자료 활용
업로드 문서는 검토 대상이고, 서버에 미리 적재한 공개 자료는 그 문서를 판단하는 근거다. 고정된 단계 순서는 유지하고, 단계 안에서 에이전트가 무엇을 찾을지와 언제 멈출지를 정한다.

| 에이전트 | 서버 자료 사용 | 찾는 것 |
|---|---|---|
| 쟁점 정리 | 사용 안 함 | 문서와 역할 카드만 보고 중립을 유지 |
| 사회자 | 사용 안 함 | 역할들이 가져온 근거만 보고 진행을 정함 |
| 토론 에이전트(역할의 첫 발언) | 답하기 전 검색 필수 | 자기 역할과 얽힌 다른 사업 조건, 제외 대상, 외부 기준, 실제 제기된 문제 |
| 토론 에이전트(이후 발언) | 필요할 때만 | 상대 주장의 전제가 자료로 확인되거나 반박되는지 |
| 최종 정리 | 답하기 전 검색 필수 | 사용자가 확인해야 할 문서 밖 조건 |
| 역할 추출 | 사용 안 함 | 역할은 입력 문서에서 뽑는다 |

규칙은 다음과 같다. 원문 인용(citation)은 언제나 입력 문서의 조항이고, 서버 자료는 sources에 따로 남긴다. 다른 자료의 내용을 입력 문서의 규정처럼 말하지 않고 기관과 회차를 밝힌다. 에이전트가 도구로 읽은 쪽만 인용할 수 있고 서버가 원문과 대조한다. 토론 발언에 남긴 서버 자료는 이후 발언자와 사회자가 함께 본다. 검색 라운드는 3회로 제한하고 상한에 닿으면 도구 없이 답한다. 서비스는 최신 공지까지 쓰고, 평가 실행은 문서 발행일 이전의 정책 자료만 본다. 입력 문서와 내용이 같은 서버 자료는 근거에서 제외한다. 사용자가 올린 문서는 서버 자료가 되지 않는다. 의견 자료의 건수를 여론이나 찬반 비율로 쓰지 않는다. 근거는 2~4쪽 디자인을 유지하기 위해 5쪽과 의견서에 표시한다.

## 비교 평가
PolicyLens의 가치를 단일 프롬프트와 비교해 확인한다. 기준선은 같은 모델과 문서에 "여기서 나는 [역할]인데, 나한테 불리한 조항 찾아줘"라고 묻는 호출 1회이며 구조화와 검증을 적용하지 않는다(화면 표시용으로 옮기는 호출은 따로 있다). 검토가 끝난 뒤 사용자가 요청하면 생성한다. 두 결과를 서식 없는 글로 나란히 보여주고 좌우 배치는 실행마다 무작위로 정한다. 기준선 답변은 그대로 저장하고, 화면에는 모델 호출 1회를 더 써서 PolicyLens 주의 조항과 같은 칸(쟁점, 이유, 원문, 영향, 다른 입장, 확인할 것, 물어볼 질문, 불확실한 부분)으로 옮겨 같은 형식으로 보여준다. 칸에는 내 해석과 상대 해석도 포함된다. 옮기는 호출은 기준선 답변만 받고 문서는 받지 않으며, 답변에 없는 칸은 비워 화면에서 뺀다. 옮긴 결과는 검증하지 않는다. 옮긴 결과가 없는 이전 실행은 마크다운 기호만 지운 답변을 보여준다. 평가를 저장한 뒤에만 방식을 공개하며 평가는 수정할 수 없다. 사용자가 PolicyLens 과정을 본 뒤 평가하므로 완전한 맹검은 아니다.

## 실행과 저장
실행 단위는 문서, 대표 역할 2~3명과 페르소나, 선택한 역할이다. 단기 저장은 실행마다 입력 정책 문서(`ReviewRun.pages`), 역할별 페르소나 스냅샷(`ReviewRun.personas`), 토론 과정과 사회자 결정(`ReviewRun.steps`), 재시도 상태다. 장기 저장은 Source 테이블의 검수된 공개 자료와 Persona 테이블의 페르소나 표본(`manage.py load_personas`)이다. 실행 당시 입력·모델·프롬프트를 고정한다. 사용자 업로드와 공개 참고자료는 접근 범위를 구분한다.

공통 문서 저장소는 분야·발행기관·지역·시행일·버전·출처를 기록하고 단계적으로 수집한다. 검토 대상이 일차 근거다. 다른 기관 문서는 비교 자료이며 적용 범위를 표시한다. 합성 토론 결과를 검증된 장기 근거로 자동 승격하지 않는다.

## 강의 구조
강의 HCI_9 기준으로 각 기능의 위치는 다음과 같다. 워크플로: 쟁점 정리 → 토론 → 마무리 → 주의 조항의 단계와 토론의 쟁점 순서·쟁점별 발언 수는 서버가 고정하고, 쟁점 안에서 다음에 누가 말할지와 새 쟁점 추가는 사회자 에이전트가 계획한다(61쪽 Planning). 비용과 실행 간 비교를 위해 서버가 발언 수와 쟁점 수를 고정한다. 에이전트 루프: 토론 에이전트와 최종 정리가 도구를 골라 쓰는 ReAct 형태의 루프이며(22, 61쪽, Lab 13쪽) Agentic RAG(52쪽)의 "자료가 더 필요한가" 판단을 따른다. 사람 확인: 역할 선택이다. 도구는 읽기 전용이라 실행 전 승인을 두지 않는다. 결과 검토(Reflection, 25–27쪽)는 형식과 인용의 재시도 1회까지이며 주장의 타당성은 검토하지 않는다. 문서에 포함된 예시 명령은 참고 데이터로 취급한다.

- server/agents/runner.py는 실행을 조정한다.
- server/agents/planning.py는 단계 순서와 토론 상한을 정의한다.
- server/agents/tools/personas.py는 역할에 맞는 페르소나를 고른다.
- server/agents/memory/는 실행 상태와 확정된 이력을 조회한다.
- server/agents/tools/는 원문 조회와 인용 확인, 서버 자료 검색과 읽기(sources.py)를 담당한다.
- prompts/는 역할 추출·쟁점 정리·사회자·쟁점 토론·최종 정리·서버 자료 사용 지침을 보관한다.
- data/raw, processed, reviewed는 수집·추출·검수 자료를 보관한다.
- server/integrations/는 외부 모델 호출을 담당한다.

## 구현 순서와 성공 기준
1. 독립 프로젝트와 데이터 모델 → 자체 가상환경과 데이터로 단독 실행 가능.
2. 문서 입력·역할 추출·선택 → 원문 인용이 일치하는 2~3개 역할과 사용자 선택이 저장됨.
3. 단계별 검토 → 순서대로 저장되고 실패 시 완료된 단계부터 재개됨. 세션별 접근 격리.
4. 쟁점 정리와 사회자 토론 → 쟁점에서 벗어난 조항을 제외하고, 쟁점마다 고른 역할이 첫 발언을 하며, 사회자가 정한 발언자가 같은 쟁점의 앞선 발언에 답함. 발언은 한 번에 하나씩 올라오고 쟁점은 처음 3개와 추가 2개, 쟁점마다 발언 3개.
5. 주의 조항과 의견서 → 원문 인용, 영향, 확인할 것, 역할별 의견서를 제공함.
   비교 평가 → 같은 문서의 단일 프롬프트 결과와 나란히 보고 평가를 저장함.
6. 실제 모델 파일럿 → 사회적으로 중요한 주제의 정책 문서로 추출과 쟁점 품질, 실패율, 시간, 비용을 측정함.
7. 운영 전환 → PostgreSQL, 워커, 동시 실행 제어, 배포.
8. 공개 정책 데이터 수집·검수·적재·검색 연결 → 출처와 적용 범위를 확인한 자료를 에이전트가 찾아 씀. 완료.
9. 평가 실행 → `evaluate`로 문서별 결과를 남기고 `score`로 대략 비교한다. 사람의 정답 확정과 채점이 남아 있다.

데이터와 평가 절차는 docs/DATA_PLAN.md를 따른다. 평가는 이해관계자 추출의 타당성, 중요한 조항 발견, 주의 이유 이해, 의견서의 활용 가능성으로 한다.
