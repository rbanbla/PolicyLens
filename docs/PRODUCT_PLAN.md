# PolicyLens v2 제품 및 구현 계획

## 과제 요구
Topic 6, Development of Stakeholder Agent Related to Policy Documents. 정책 문서에 피드백을 제출할 수 있는 이해관계자 에이전트, 이해관계자 추출 요구사항 도출, 입장 제시와 토론 환경, 사회적으로 중요한 주제의 국내외 정책 데이터를 요구한다.

## 목적과 가정
정책 문서가 내 입장에 미치는 영향을 이해하고 주의할 조항을 찾는 서비스다. 정책 문구는 사용자가 바꾸기 어려우므로 수정안을 만들지 않는다. 입력은 공공정책 문서이며 부동산, 세금, 청년 등 주제는 코드에 고정하지 않는다. 대부분의 조항은 자명하므로 논쟁 지점을 찾아 그곳만 토론한다. 로컬 SQLite를 사용하며 운영 DB 목표는 PostgreSQL이다.

## 다섯 페이지
1. 정책 문서를 입력한다.
2. 문서 유형, 정책 분야, 목적, 적용 대상, 요약과 대표 이해관계자 2~3명을 제시한다. 사용자가 역할을 확인하고 자신의 입장을 고른다. 문서에 직접 언급되지 않은 역할은 그 사실을 표시한다.
3. 역할별 독립 입장을 채팅으로 보여주고, 쟁점 정리 결과와 제외한 내용을 아래에 제시한다. 역할이 차례로 돌아가며 모델 호출 한 번에 의견 하나씩 올리고(역할당 최대 3개), 쟁점 정리는 최대 3개를 고른다. 더 낼 것이 없는 역할의 남은 차례는 호출 없이 건너뛴다.
4. 쟁점마다 사용자가 고른 역할이 자기에게 불리한 점을 먼저 말하고, 다른 역할들은 그 발언을 읽고 수용·제한·반박으로 답한다. 셋째 발언자는 앞선 답변에도 반응한다. 쟁점 하나에 모든 역할이 말한 뒤 다음 쟁점으로 넘어간다. 고른 역할이 정보로 전달되지는 않고 발언 순서만 정한다.
5. 내 입장에서 주의할 조항을 보여준다. 해당 조항, 내게 미치는 영향, 쟁점 유형, 다른 역할의 시각, 확인할 것, 담당 기관에 물어볼 질문, 불확실한 부분을 포함한다. 역할별 의견서를 함께 제공한다. 법률·세무 자문이 아니라는 안내를 표시한다.

## 이해관계자 추출 요구사항
1. 포함: 문서가 권리·의무·혜택·부담·결정권을 배분하거나 그 결과를 직접 받는 집단이다.
2. 대표 선정: 이해가 서로 다른 집단 2~3개. 동의어는 함께 고르지 않는다. 같은 집단이라도 조항이 조건에 따라 다른 결과를 주면 사용자가 미리 자기 위치를 알 수 있는 조건 하나로 나누되, 집행기관이나 결정권자의 자리는 남긴다. 결과가 갈리지 않는 하위 분류는 함께 고르지 않고 나머지는 기타 이해관계자로 기록한다.
3. 다양성: 가능하면 수혜자·부담자·집행자를 섞는다. 고정된 이름을 강제하지 않는다.
4. 근거 유형: 문서에 언급된 explicit과, 언급은 없지만 조항의 효과가 직접 미치는 implied를 구분한다. 둘 다 원문 조항을 인용한다.
5. 근거 부족: 둘 이상 찾지 못하면 역할을 지어내지 않고 이유를 안내한다.

## 쟁점 판별
주제가 아니라 조항의 구조로 판별한다. 이해 충돌, 모호성, 재량 집중, 경계·배제, 부담 전가, 누락의 여섯 유형이다. 어디에도 해당하지 않는 정의, 시행일, 단순 절차는 제외하고 제외 내용을 기록한다. 누락 지적은 관련 조항을 인용하되 문서에 없는 내용임을 밝힌다.

## 검토 원칙
언급 횟수나 다수결로 쟁점이나 편향을 확정하지 않는다. 서버는 원문 인용, 서버 자료 인용, 참조 범위를 검증한다. 역할 에이전트는 자기 카드만 받고 사용자의 선택은 최종 단계에만 전달해 독립성을 지킨다. 역할들의 일치는 사실 검증이 아니다. 판단할 수 없는 사항은 질문과 불확실성으로 남긴다.

## 서버 자료 활용
업로드 문서는 검토 대상이고, 서버에 미리 적재한 공개 자료는 그 문서를 판단하는 근거다. 고정된 단계 순서는 유지하고, 단계 안에서 에이전트가 무엇을 찾을지와 언제 멈출지를 정한다.

| 에이전트 | 서버 자료 사용 | 찾는 것 |
|---|---|---|
| 역할 에이전트 | 답하기 전 검색 필수 | 자기 역할과 얽힌 다른 사업 조건, 제외 대상, 외부 기준, 실제 제기된 문제 |
| 쟁점 정리 | 사용 안 함 | 역할들이 가져온 근거만 대조해 중립을 유지 |
| 토론 에이전트 | 필요할 때만 | 상대 주장의 전제가 자료로 확인되거나 반박되는지 |
| 최종 정리 | 답하기 전 검색 필수 | 사용자가 확인해야 할 문서 밖 조건 |
| 역할 추출 | 사용 안 함 | 역할은 입력 문서에서 뽑는다 |

규칙은 다음과 같다. 원문 인용(citation)은 언제나 입력 문서의 조항이고, 서버 자료는 sources에 따로 남긴다. 다른 자료의 내용을 입력 문서의 규정처럼 말하지 않고 기관과 회차를 밝힌다. 에이전트가 도구로 읽은 쪽만 인용할 수 있고 서버가 원문과 대조한다. 독립 입장 단계에서는 자기 검색 결과만 보고, 쟁점 단계부터 공유한다. 검색 라운드는 3회로 제한하고 상한에 닿으면 도구 없이 답한다. 서비스는 최신 공지까지 쓰고, 평가 실행은 문서 발행일 이전의 정책 자료만 본다. 입력 문서와 내용이 같은 서버 자료는 근거에서 제외한다. 사용자가 올린 문서는 서버 자료가 되지 않는다. 의견 자료의 건수를 여론이나 찬반 비율로 쓰지 않는다. 근거는 2~4쪽 디자인을 유지하기 위해 5쪽과 의견서에 표시한다.

## 비교 평가
PolicyLens의 가치를 단일 프롬프트와 비교해 확인한다. 기준선은 같은 모델과 문서에 "여기서 나는 [역할]인데, 나한테 불리한 조항 찾아줘"라고 묻는 호출 1회이며 구조화와 검증을 적용하지 않는다. 검토가 끝난 뒤 사용자가 요청하면 생성한다. 두 결과를 서식 없는 글로 나란히 보여주고 좌우 배치는 실행마다 무작위로 정한다. 기준선은 표시할 때 마크다운 기호만 지우고 저장된 답변은 바꾸지 않는다. 평가를 저장한 뒤에만 방식을 공개하며 평가는 수정할 수 없다. 사용자가 PolicyLens 과정을 본 뒤 평가하므로 완전한 맹검은 아니다.

## 실행과 저장
실행 단위는 문서, 대표 역할 2~3명, 선택한 역할이다. 단기 메모리는 현재 실행의 확정된 결과와 재시도 상태, 장기 저장은 Source 테이블의 검수된 공개 자료다. 실행 당시 입력·모델·프롬프트를 고정한다. 사용자 업로드와 공개 참고자료는 접근 범위를 구분한다.

공통 문서 저장소는 분야·발행기관·지역·시행일·버전·출처를 기록하고 단계적으로 수집한다. 검토 대상이 일차 근거다. 다른 기관 문서는 비교 자료이며 적용 범위를 표시한다. 합성 토론 결과를 검증된 장기 근거로 자동 승격하지 않는다.

## 강의 구조
강의 HCI_9 기준으로 각 기능의 위치는 다음과 같다. 워크플로: 단계 순서는 서버가 고정하며(61쪽의 자율 계획은 쓰지 않는다) 역할 독립성과 실행 간 비교를 지키기 위해서다. 에이전트 루프: 역할 에이전트, 토론, 최종 정리가 도구를 골라 쓰는 ReAct 형태의 루프이며(22, 61쪽, Lab 13쪽) Agentic RAG(52쪽)의 "자료가 더 필요한가" 판단을 따른다. 사람 확인: 역할 선택이다. 도구는 읽기 전용이라 실행 전 승인을 두지 않는다. 결과 검토(Reflection, 25–27쪽)는 형식과 인용의 재시도 1회까지이며 주장의 타당성은 검토하지 않는다. 문서에 포함된 예시 명령은 참고 데이터로 취급한다.

- server/agents/runner.py는 실행을 조정한다.
- server/agents/planning.py는 순서와 종료를 정의한다.
- server/agents/memory/는 실행 상태와 확정된 이력을 조회한다.
- server/agents/tools/는 원문 조회와 인용 확인, 서버 자료 검색과 읽기(sources.py)를 담당한다.
- prompts/는 역할 추출·독립 입장·쟁점 정리·쟁점 토론·최종 정리·서버 자료 사용 지침을 보관한다.
- data/raw, processed, reviewed는 수집·추출·검수 자료를 보관한다.
- server/integrations/는 외부 모델 호출을 담당한다.

## 구현 순서와 성공 기준
1. 독립 프로젝트와 데이터 모델 → 자체 가상환경과 데이터로 단독 실행 가능.
2. 문서 입력·역할 추출·선택 → 원문 인용이 일치하는 2~3개 역할과 사용자 선택이 저장됨.
3. 단계별 검토 → 순서대로 저장되고 실패 시 완료된 단계부터 재개됨. 세션별 접근 격리.
4. 쟁점 정리와 토론 → 쟁점에서 벗어난 조항을 제외하고, 고른 역할이 연 발언에 다른 역할이 모든 쟁점에서 답함. 의견은 한 번에 하나씩 차례로 올라오고 역할당 의견과 쟁점은 최대 3개.
5. 주의 조항과 의견서 → 원문 인용, 영향, 확인할 것, 역할별 의견서를 제공함.
   비교 평가 → 같은 문서의 단일 프롬프트 결과와 나란히 보고 평가를 저장함.
6. 실제 모델 파일럿 → 사회적으로 중요한 주제의 정책 문서로 추출과 쟁점 품질, 실패율, 시간, 비용을 측정함.
7. 운영 전환 → PostgreSQL, 워커, 동시 실행 제어, 배포.
8. 공개 정책 데이터 수집·검수·적재·검색 연결 → 출처와 적용 범위를 확인한 자료를 에이전트가 찾아 씀. 완료.
9. 평가 실행 → `evaluate`로 문서별 결과를 남기고 `score`로 대략 비교한다. 사람의 정답 확정과 채점이 남아 있다.

데이터와 평가 절차는 docs/DATA_PLAN.md를 따른다. 평가는 이해관계자 추출의 타당성, 중요한 조항 발견, 주의 이유 이해, 의견서의 활용 가능성으로 한다.
