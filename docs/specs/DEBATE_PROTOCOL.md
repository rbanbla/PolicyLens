# PolicyLens 에이전트 토론 프로토콜 제안

문서와 사례는 [사용자 문서 입력 규격](../../study/README.md)을 따른다. 3절의 고려대 사례는 흐름 설명용 예시다. 현재 A와 수집 자료 기반 잠정 B를 연결했다. 행정 직접 의견 부족과 최신 데이터 사용 범위는 [현행 실행 명세](DATA_CONNECTION.md)를 따른다.

**결정안** · 기존 조건당 7회 구조를 기준선으로 두고, 첫 연구용 후보는 **독립 입장 3 → 교차 반론 3 → 공동 초안 1 → 역할별 조항 검토 3 → 최종 편집 1**로 설계한다. 조건당 11회, A/B 토론 한 쌍당 22회다. 현재 구현은 공통 쟁점 발견 4회를 먼저 실행하여 최대 26회다. 추가 4회는 진행자가 쓴 문구를 당사자 역할이 읽고 자신의 우려가 해결됐는지 밝히는 데 쓴다. 참여자가 보는 화면 수는 늘리지 않는다. 아래는 구현 명세이며 성능을 측정한 결과는 아니다.

## 2. 메시지 계약과 실행 순서

공통 입력은 정책 버전·허용 조항 ID, 한 가지 사례, 승인된 역할 카드 세 장, 언어·모델·추론 설정·길이 상한이다. 카드에는 관련 직무나 학습 맥락만 넣는다. 각 역할의 비공개 입력은 A에서 상세 역할 지침, B에서 해당 역할에 배정한 승인 의견 발췌문이다. 발언자에게는 자기 카드와 비공개 입력만 주고 타 역할에 대해서는 역할명과 공개 발언만 준다. 조건 사이의 대화 기록은 완전히 분리한다. B에 필요한 자료가 없는 역할이 있으면 연구용 쌍을 시작하지 않는다.

| 단계 | 요청당 입력 | 필수 출력과 규칙 |
|---|---|---|
| 입장 ×3 | 공통 사례·조항 + 자기 카드·조건별 입력 | 쟁점 한 개, 제안 한 개, 이유, 수용 조건, 조항 ID. B에서 자료로 뒷받침하는 주장에는 배정된 의견 ID를 붙인다. 제안과 원문에 있는 의무를 구분한다. |
| 교차 반론 ×3 | 위 입력 + 확정된 입장 세 개의 공개 필드 | 대상 주장 ID, 상대 주장 요지, 반응 유형, 구체 사례, 자기 입장을 유지하거나 바꿀 조건. 서버가 주 응답 대상을 한 명씩 배정한다. 학생은 교수에게, 교수는 행정에게, 행정은 학생에게 답하는 식이다. 같은 A/B 쌍에서는 같은 배정표를 쓴다. 다른 중요한 주장은 보조 대상으로도 참조할 수 있다. |
| 초안 ×1 | 정책 원문 + 입장·반론 여섯 개의 공개 필드 | 조항별 초안 문장 ID, 제안 문구, 관련 주장 ID, 반영했거나 보류한 우려. 진행자는 원칙·사실을 보충하는 권한이 없다. 출처가 없는 새 의무는 편집 제안으로 표시하거나 보류한다. |
| 조항 검토 ×3 | 동일한 초안 + 공개 토론 + 자신의 원래 입력 | 문장별 ‘수용·조건부 수용·반대·판단 유보’, 이유, 필요한 최소 변경 문구. 다른 역할의 검토 결과는 보지 않는다. 평가 대상을 초안 버전과 문장 ID로 고정한다. |
| 최종 편집 ×1 | 초안 + 세 검토 + 조항·공개 발언 | 최종 문장, 원문 대비 변경, 반영한 검토 ID, 반영하지 않은 요구와 이유. 충돌하는 요구를 억지로 합칠 필요가 없다. 하나로 정하기 어렵다면 선택지와 판단 조건을 남긴다. |

**종료 규칙** · 최종 편집 한 번으로 끝낸다. 세 역할이 같은 초안 문장을 모두 명시적으로 수용하고 최종 문구가 그대로일 때만 ‘세 역할이 수용한 문구’라고 표시한다. 조건부·유보·무응답은 동의에 포함하지 않는다. 편집 후 새로 바뀐 문장은 ‘검토를 반영한 제안’으로 표시한다. 그 문구에 재투표한 기록은 없기 때문이다.

### 프롬프트 예시

- **교차 반론** · “지정된 주장 한 개를 상대가 받아들일 표현으로 요약하세요. 자신의 역할에서 그 제안이 곤란해지는 과제 상황 하나, 또는 실제로 수용할 조건 하나를 제시하세요. 다른 역할의 의도나 경험을 추정하지 마세요. 지정된 ID와 공개할 짧은 이유를 반환하세요.”
- **조항 검토** · “초안의 어느 문장이 처음 제기한 우려를 해결했습니까? 부분적으로 해결했다면 부족한 단어 또는 조건을 지목하고 최소 변경을 제안하세요. 근거가 없으면 판단을 유보하세요.”
- **최종 편집** · “각 검토 요구에 반영·부분 반영·보류 중 하나를 기록하세요. 최종 문장이 달라졌다면 변경 전 초안에 대한 지지를 최종 문장의 동의로 표시하지 마세요.”

## 3. 한 조항이 바뀌는 예

아래는 흐름 확인용 모의 사례다. 고려대 §4.4의 도구·시점·범위 및 AI 기여 공개 요구를 공통 입력으로 두고, 학생이 맞춤법 교정과 논리 구조 제안을 모두 이용한 과제를 검토한다. 원문 PDF의 로컬 수집본은 `research/2026-11-02/KR/korea.pdf`에 있다(배포 제외).

1. 학생의 주장 S1은 모든 사용을 밝히되 단순 교정의 기록 부담을 줄이자는 것이다. 교수의 P1은 평가 대상인 논리 구성을 누가 했는지 확인하자는 것이다. 행정의 A1은 과제마다 제출 양식이 늘어나지 않도록 공통 항목을 두자는 것이다.
2. 학생은 P1을 읽고 “논리 구성을 바꾼 경우에는 반영 부분을 적되 맞춤법 교정에도 같은 설명이 필요한가?”라고 묻는다. 이 반론은 P1을 참조한다.
3. 진행자는 기본 공개 항목을 유지하고 “내용 생성 시 검증 과정을 덧붙인다”는 초안 D1을 낸다. 교수 역할은 D1의 ‘내용 생성’이 기존 문장 재배열까지 포함하는지 모호하다며 조건부 수용한다.
4. 최종 편집자는 ‘주장 또는 논리 순서를 바꾼 경우’를 명시한다. 모바일에는 **바뀐 문구 → 교수의 조건부 검토 → D1과 처음의 P1 → §4.4**를 연결한다. 학문 분야별 경계 예시가 필요하다는 요구가 남으면 별도 이견으로 제시한다.

## 4. 서버와 DB

Django 관리 API가 실행 쌍을 생성하면 Python 워커가 단계별 요청을 보낸다. 병렬인 단계는 각 역할 출력이 전부 검증된 뒤 다음 단계로 넘어간다. 상태 순서는 queued → openings → replies → draft → reviews → final → researcher_review → published다. 한쪽이라도 실패하면 쌍의 게시를 잠근다.

- **실행 명세** · pair_id, run_id, 조건, protocol_version, policy_version, 역할 카드 버전, 자료 묶음 버전, 모델·설정, 배정표를 고정한다. 이후 설정 변경은 새 실행으로 만든다.
- **발언과 관계** · 역할별 요청은 (run_id, stage, role)을 고유 키로 둔다. 한 요청에 여러 문장이 올 수 있으므로 서버가 각 주장·초안 문장에 ID를 발급한다. 관계 테이블은 원본 ID, 대상 ID, 관계 종류를 보존한다. 서로 다른 실행 또는 아직 확정되지 않은 대상은 참조할 수 없다.
- **비공개 근거** · 의견 발췌 ID와 원문은 별도 테이블에 둔다. 다음 역할에는 공개 발언과 조항 ID만 전달한다. 참여자 조회 API는 검수·게시된 공개 필드로만 응답한다.
- **재시도** · 요청 키와 입력 해시가 같은 성공 결과는 재사용한다. 제한·일시 장애는 간격을 늘려 최대 두 번 재시도한다. 잘못된 참조는 검증 오류를 알려 한 번 수정하게 하고 다시 실패하면 연구자 검수로 보낸다. 재시도는 기본 22회와 별도로 기록한다.

## 5. 더 복잡한 구조를 유지할지 정하는 파일럿

먼저 같은 쟁점에서 A·B 각각 초안까지 생성한다. 이 시점의 결과가 기존 7회 기준선이다. **같은 여섯 발언과 같은 초안**에서 검토·편집만 이어서 실행하면 초안과 최종안의 차이를 따로 볼 수 있다. 다른 토론을 처음부터 두 번 생성하면 운 좋게 나온 발언의 효과가 섞인다. 이 내부 점검과 참여자의 A/B 선호 실험은 분리한다.

| 셀프체크 | 판정 방식 |
|---|---|
| 반론이 상대의 말에 의존하는가 | 검수자가 세 반론마다 상대가 실제로 제시한 구절과 그에 대한 응답을 표시한다. 다른 역할 이름만 바꿔도 성립하는 일반론은 재검토한다. 선택 검증으로 상대 발언만 숨겨 다시 생성해 어떤 구체적 대응이 사라지는지 비교한다. |
| 추가 4회가 유용한가 | 미리 고른 서로 다른 경계 사례 세 개에서 초안·최종안을 생성 순서를 가리고 비교한다. 두 팀원이 독립적으로 ‘빠진 조건 복구·모호한 경계 명시·미합의 보존’을 기록한다. 세 사례 중 두 개 이상에서 근거 있는 개선을 확인하고 새 중대 오류가 없을 때 11회안을 유지한다. 이는 팀의 채택 기준 제안이다. |
| 게시할 수 있는가 | 잘못된 조항·발언 참조, B 자료 의미 왜곡, 가공한 합의, 조건 단서 노출은 각각 0건이어야 한다. 새 문장을 넣었으나 연결 근거가 없으면 게시를 보류한다. |
| 모바일에서 효과가 보이는가 | 예비 사용자가 문구가 바뀐 이유를 설명하고 그 변화를 일으킨 검토 발언을 찾는지 관찰한다. 초안 전체는 접어 두고 변경점·이견을 먼저 보여준다. |

구현 순서는 모의 사례로 참조·상태 검증 → 7회 기준선 → 초안 검토·최종 편집 추가 → 블라인드 내부 검수 → 프로토콜 하나 고정 → 30명 미만 참여자 평가다. A에는 7회, B에는 11회를 적용하면 입력 방식과 토론 방식의 효과가 섞이므로 본 평가에서는 두 조건에 같은 프로토콜을 쓴다.
